# Снапшоты игроков — шаг 4.5

Сервер собирает состояние после симуляции игроков, раз в два физических тика (30 Гц при 60 Гц).
Один RPC `SnapshotStream.receive_snapshot` с `authority/call_remote/unreliable_ordered`, канал 2,
отправляется каждому владельцу сущности, прошедшему handshake и `map_ready`.
Снапшоты не заменяют надёжное появление/удаление через MultiplayerSpawner.

## Формат little-endian

| Смещение | Поле | Размер |
| --- | --- | --- |
| 0 | Серверный тик | uint32 |
| 4 | Количество игроков | uint16 |
| 6 | Последний обработанный **исходный** тик ввода получателя | uint32 |
| 10 | Записи игроков | 25 × количество байт |

| Смещение в записи | Поле | Размер |
| --- | --- | --- |
| 0 | ENet peer id игрока | uint32 |
| 4 | Мировая позиция XYZ | 3 × uint16 |
| 10 | Скорость XYZ | 3 × uint16 |
| 16 | Yaw, циклический диапазон −π…π | uint16 |
| 18 | Pitch, диапазон −π/2…π/2 | uint16 |
| 20 | Стойка и флаги | uint8 |
| 21 | Идентификатор оружия | uint32 |

Стойка занимает биты 0–1 (STAND/CROUCH/PRONE; 3 недопустимо). Остальные биты:
2 — grounded, 3 — sprinting, 4 — aiming, 5 — dead, 6 — downed. Бит 7 запрещён.
Оружие — стабильный 32-битный `StringName.hash()` существующего `WeaponData.id`, 0 — оружия нет.
Коллизии и нулевые хеши всех текущих оружейных профилей проверяются тестом.
Клиент хранит идентификатор как данные представления; он не меняет Inventory или боезапас.
При добавлении профилей тест коллизий должен проходить до использования нового id.

[SnapshotConfig](../src/net/snapshot_config.gd) задаётся через ресурс карты [MapData](../src/maps/map_data.gd).
[Стандартный профиль](../src/net/default_snapshot.tres): позиции X/Z −256…256 м, Y −64…192 м,
скорость каждой оси −64…64 м/с. Округление к ближайшему uint16 с насыщением на границах.
Максимальная ошибка: X/Z 3.907 мм, Y 1.954 мм, скорость 0.977 мм/с, yaw 0.002747°, pitch 0.001374°.
Границы карты должны вмещать её игровое пространство; выход за них насыщается, а не оборачивается.

Проверяется точный размер пакета, положительный серверный тик, ограниченное количество записей,
валидные peer id, уникальность id и допустимые флаги. Весь пакет проверяется до публикации.
Повторный/старый тик игнорируется. Неизвестная ещё сущность пропускается: следующий полный снапшот
заполнит буфер после надёжного спавна. RPC принимает только сервер; input authority не даёт права
отправлять состояние. `accept_packet` — внутренний метод декодирования, RPC не экспортирует его.

## Представление

[RemoteInterpolator](../src/net/remote_interpolator.gd) хранит 32 заранее созданные записи в кольце.
Приём копирует состояние в слот; общий временный объект декодера не сохраняется по ссылке.
Выборка пишет в объект вызывающего кода и не создаёт словари, массивы или узлы.

Целевое время — `Net.clock.estimated_server_tick(now) − 0.1 × physics_ticks_per_second`.
Опережающий клиентский `Net.tick` для этого не используется. У listen-host берётся собственный
серверный тик плюс доля физического кадра. Позиция/скорость интерполируются линейно,
yaw — `lerp_angle` через короткую дугу, pitch — линейно; дискретные поля меняются на границе записи.
Перед первой записью удерживается первая поза. После последней позиция продолжается по скорости
максимум 100 мс, затем остаётся в этой предельной точке до поступления новых данных.

[RemotePlayerView](../src/player/remote_player_view.gd) — мировой `top_level` узел с выключенной
интерполяцией физики движка: второй слой сглаживания не добавляется. Кешированная капсула меняет
высоту по стойке, процедурный указатель показывает yaw/pitch. Корень Player, хитбоксы, Inventory,
здоровье и симуляция клиента этой косметикой не изменяются. Свой игрок получает подтверждение ввода,
но его поза остаётся исходной: предсказание и reconciliation не реализованы в 4.5.
При выходе карта удаляет сущности/буферы и обнуляет состояние транспорта.

## Воспроизводимая приёмка

- [Модульные тесты](../tests/unit/net/) проверяют квантование/границы/повреждения пакетов,
  атомарность, повторные/старые записи, кольцо, пропуски, ±π, задержку и предел экстраполяции.
- [Межпроцессный тест](../tests/integration/test_snapshots.gd) запускает выделенный сервер + восемь
  настоящих клиентов, затем listen-host + два клиента; последний подключается позже.
- [snapshot_worker.gd](../tools/snapshot_worker.gd) использует настоящее меню, карту, ввод и RPC.
  Выборки сопоставляются с серверным логом того же тика; отдельно проверяются подтверждение именно
  своего ввода, отсутствие клиентской симуляции и заморозка представления после остановки снапшотов.
- Период отправки проверяется по каждому серверному событию, включая кадры без подробного лога.
  Ненадёжный транспорт вправе терять пакеты: частота приёма не является частотой отправки.
- После прогрева ENet измеряются четыре секунды: `ENetConnection.pop_statistic` для
  `HOST_TOTAL_RECEIVED_DATA` и `HOST_TOTAL_RECEIVED_PACKETS`. Счётчик байтов включает весь входящий
  UDP payload (ENet, RPC, часы и подтверждения), а не только декодированные снапшоты.
  Добавление 28 байт на датаграмму учитывает IPv4 + UDP; Ethernet/VPN overhead не включён.
- Полезная нагрузка при восьми игроках: `(10 + 8 × 25) × 30 = 6300 байт/с`.
  Фактический результат приёмки записывается в [ARCHITECTURE.md](../ARCHITECTURE.md).

Визуальный прогон использует тот же worker без `--headless`, с `--capture=<абсолютный путь PNG>`.
Ему и остальным workers передаются общий порт, ожидаемое число игроков, пути `--pause-file` и
`--stop-file`. После появления `SNAP MEASURE` у клиентов создаётся pause-file; после снимков и
`SNAP DONE` сначала завершаются клиенты, затем сервер. Генерируемые логи/снимки находятся в `.godot/`.
