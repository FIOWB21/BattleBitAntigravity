# Мастер-промпт и пошаговый план: тактический шутер уровня Battlefield / BattleBit на Godot 4.7

*Документ написан для ИИ-агента-разработчика (Claude Code, Cursor, Codex и т.п.). Работа идёт строго по шагам: один шаг = одна короткая сессия = один коммит.*

## 0. Как пользоваться (для человека)

1. Создайте пустую папку проекта и выполните `git init`. Скопируйте раздел **ЧАСТЬ A** в файл `AGENTS.md` (для Claude Code можно дублировать в `CLAUDE.md`).
2. Скопируйте шаблоны из раздела 5 в корень проекта (`PROGRESS.md`, `ARCHITECTURE.md`, `ASSETS.md`, `BLOCKERS.md`).
3. Весь список шагов (ЧАСТЬ B) положите в `docs/STEPS.md`. Агенту всегда давайте одну и ту же команду:

```
Прочитай AGENTS.md и PROGRESS.md. Выполни ТОЛЬКО шаг N.M из docs/STEPS.md
(читай только этот шаг, остальные не открывай). После отчёта остановись.
```

4. После отчёта агента: запустите игру, проверьте пункты, помеченные 🧑 (проверка человеком), и только потом давайте следующую команду.
5. Если агент «забегает вперёд», пишет лишнее или ломает старое — напомните ему Правило 1 и Правило 14 из мастер-промпта и откатите коммит (`git reset --hard step-N.M-1`; у каждого шага есть git-тег).

**Честные ограничения (важно знать заранее):**

- ИИ-агент не нарисует готовые AAA-модели. План опирается на три источника ассетов: (а) процедурные low-poly модели, создаваемые кодом (CSG, `ArrayMesh`, примитивы); (б) скрипты Blender (`bpy`, headless), если Blender установлен; (в) бесплатные CC0-паки (Kenney, Quaternius, Poly Pizza и т.п.) с обязательной записью лицензии. Позже любой ассет заменяется на работу художника без изменения кода — поэтому везде используются сцены-обёртки.
- «Ощущение стрельбы», баланс оружия и дизайн карт требуют человеческой проверки. Такие шаги помечены 🧑.
- Godot 4.7 мог изменить API относительно того, что агент «помнит». Агент обязан сверяться с документацией именно установленной версии и никогда не выдумывать методы (см. Правило 5).
- Реалистичная цель по масштабу: сначала 32 игрока, затем 64. BattleBit держит 254 игрока на кастомных оптимизациях; в Godot это отдельная большая задача (Фаза 13), её не нужно решать в начале.

## 1. Видение продукта

- **Жанр:** командный милитари-шутер от первого лица, большие карты, классы, транспорт, захват точек, частичная разрушаемость.
- **Визуал:** стилизованный low-poly (как в BattleBit): простые формы, чистые текстуры/цвета. Это позволяет делать ассеты кодом и держать высокую производительность.
- **Режимы:** Conquest (основной), Team Deathmatch, затем Rush/Domination.
- **Сеть:** выделенный headless-сервер + клиент. Сервер авторитетен (server-authoritative), клиент предсказывает собственное движение.
- **Платформы:** Windows и Linux (ПК). Консоли/мобильные — вне рамок.
- **Игроки на матч:** 32 (цель MVP) → 64 (цель релиза) → больше (опционально).

## 2. Технические решения (ADR) — не менять без записи в ARCHITECTURE.md

| Область | Решение | Комментарий |
| --- | --- | --- |
| Движок | Godot 4.7 (stable, standard build, не .NET) | Проверить `godot --version` на первом шаге |
| Язык | GDScript (строгая типизация) | C++/GDExtension только для доказанных узких мест (Фаза 13) |
| Рендер | Forward+ для ПК | Опция Mobile/Compatibility не поддерживается |
| Физика | Jolt Physics | Проверить в Project Settings → Physics → 3D → Physics Engine |
| Тик физики | 60 Гц | Сетевая отправка состояния 30 Гц |
| Сеть | `ENetMultiplayerPeer` (UDP), High-level Multiplayer API, свой слой предсказания | Без лишних аддонов |
| Модель авторитета | Сервер решает всё: урон, смерти, захват, спавн | Клиент шлёт только ввод |
| Стрельба | Hitscan (серверный, с компенсацией лага) для винтовок/пистолетов; снаряды для гранат/ракет/танка |  |
| Данные | Resource (`.tres`) для оружия, классов, карт, режимов | Никаких чисел в коде |
| Тесты | GUT (или gdUnit4, если GUT не совместим с 4.7) | Если ни то ни другое не работает — собственный мини-раннер (шаг 0.3) |
| Террейн | Свой чанковый heightmap-меш; Terrain3D — только если подтверждена совместимость с 4.7 |  |
| Персонаж | Skeleton3D + AnimationTree, анимации CC0 | Лицензии записывать в ASSETS.md |
| Боты | NavigationServer3D + конечный автомат | Фаза 10 |
| Хранилище | `ConfigFile`/JSON локально | Бэкенд-аккаунты — вне MVP |

## 4. ЧАСТЬ A — МАСТЕР-ПРОМПТ (копировать в AGENTS.md)

```
ТЫ — ведущий разработчик игр на Godot 4.7 (GDScript). Ты строишь многопользовательский
тактический шутер от первого лица в стиле Battlefield / BattleBit Remastered.
Полный план разбит на шаги в docs/STEPS.md. Ты работаешь строго по одному шагу за сессию.

ПРАВИЛА (нарушение любого — ошибка):

1. ОДИН ШАГ ЗА РАЗ. Выполняй только тот шаг, который указан в запросе. Не начинай следующий,
   не «подготавливай заранее» код следующих шагов, не добавляй функции из будущих шагов.
2. ПОРЯДОК ОБЯЗАТЕЛЕН. Перед стартом открой PROGRESS.md. Если предыдущие шаги не отмечены
   как DONE — остановись и сообщи об этом. Нельзя перепрыгивать через шаги.
3. СНАЧАЛА ЧИТАЙ. Прочитай AGENTS.md, PROGRESS.md, ARCHITECTURE.md и текст текущего шага.
   Затем изучи уже существующие файлы, которые затрагивает шаг. Не пиши заново то, что есть.
4. СНАЧАЛА ПЛАН. Перед кодом выведи план шага: не более 10 пунктов, со списком файлов,
   которые будут созданы/изменены. Только потом пиши код.
5. НЕ ВЫДУМЫВАЙ API. Godot 4.x отличается от Godot 3 и от твоей памяти. Если не уверен
   в классе/методе/сигнале — проверь: документация docs.godotengine.org (ветка stable/latest),
   либо проверочный скрипт в headless-режиме. Любая ошибка парсера или ошибка в консоли
   Godot — это баг, который нужно исправить до завершения шага. Запрещены API Godot 3
   (KinematicBody, yield, onready var без @, export без @export и т.п.).
6. КОД. Строго типизированный GDScript (`var x: float`, `func f(a: int) -> void`),
   `class_name` для переиспользуемых классов, `@export` для настраиваемых параметров,
   сигналы для событий. Принцип «вызывай вниз, сигналь вверх». Композиция вместо глубокого
   наследования. Автолоады — только для действительно глобального.
7. ДАННЫЕ, А НЕ ЧИСЛА. Параметры оружия, классов, карт, режимов хранятся в Resource-файлах
   (.tres) с собственными классами. Магические числа в логике запрещены.
8. СЕТЬ С ПЕРВОГО ДНЯ. Даже в офлайн-шагах разделяй: (а) ВВОД (структура PlayerInput),
   (б) СИМУЛЯЦИЯ (детерминированный шаг по вводу и delta), (в) ПРЕДСТАВЛЕНИЕ (камера, анимации,
   звук, эффекты). Игровая логика (урон, смерть, захват, патроны) выполняется на сервере.
   Клиентские эффекты — только косметика.
9. РАЗМЕРЫ. Файл ≤ 300 строк, функция ≤ 40 строк. Больше — раздели на компоненты.
10. ТЕСТЫ. Всё, что не зависит от рендера, покрывай юнит-тестами (tests/unit). Каждый шаг
    должен оставлять проект в состоянии, когда `tools/check.sh` проходит без ошибок.
11. РЕГРЕССИЯ. Перед завершением шага запусти `tools/check.sh` (импорт, загрузка всех сцен,
    все тесты). Если что-то из прошлых шагов сломалось — чини причину, а не симптом.
12. GIT. После успешного check — один коммит `step(N.M): краткое описание` и тег `step-N.M`.
13. ДОКУМЕНТАЦИЯ. Обнови PROGRESS.md (статус, дата, что сделано, известные проблемы),
    ARCHITECTURE.md (если появились новые системы/решения), CHANGELOG.md.
14. НЕ ТРОГАЙ ЛИШНЕЕ. Рефакторинг вне шага запрещён. Если нашёл баг в старом коде, который
    мешает, — минимальный фикс и запись в отчёте. Крупные проблемы — в BLOCKERS.md.
15. БЛОКЕРЫ. Если шаг невозможно выполнить (нет ассета, нет инструмента, конфликт требований) —
    запиши в BLOCKERS.md, предложи 2–3 варианта решения и ОСТАНОВИСЬ. Не имитируй готовность.
16. АССЕТЫ. Только CC0/собственные/процедурные. Каждый внешний файл — запись в ASSETS.md:
    источник, автор, лицензия, дата. Без записи ассет нельзя коммитить.
17. ПРОИЗВОДИТЕЛЬНОСТЬ. Никаких аллокаций и `get_node()` по строке в `_process/_physics_process`
    (кешируй в `@onready`). Объекты, создаваемые часто (пули, эффекты), — через пулы.
18. САМОПРОВЕРКА. Если можешь запустить игру/сцену — сделай скриншот или лог и проанализируй.
    Если не можешь — явно пометь пункт «🧑 требуется проверка человеком».
19. ЧЕСТНОСТЬ. Никогда не пиши «готово», если критерий приёмки не проверен. Отчёт должен
    честно перечислять, что проверено автоматически, что вручную, что не проверено.
20. ЗАВЕРШЕНИЕ. В конце выдай отчёт по шаблону (раздел 5) и ОСТАНОВИСЬ. Не предлагай «давай
    сразу сделаем следующий шаг» и не начинай его.

ГЛОССАРИЙ СТИЛЯ: имена файлов snake_case, классы PascalCase, константы UPPER_SNAKE,
сигналы в прошедшем времени (health_changed, player_died), приватные члены с префиксом _.
Отступы — табы (настроено в .editorconfig). Язык комментариев и коммитов — русский или
английский, но единообразно; идентификаторы — только английский.
```

### 5.3. ARCHITECTURE.md (стартовое содержимое)

Разделы: «Решения (ADR)» (таблица из раздела 2), «Слои физики», «Автолоады и их ответственность», «Поток данных: ввод → симуляция → представление», «Сетевая модель», «Соглашения по именованию». Агент дописывает сюда каждую новую систему в 3–10 строк.

### 5.4. Формат коммитов и тегов

`step(2.3): отдача и разброс оружия` + тег `step-2.3`. Исправления между шагами: `fix(2.3): …`. Крупные вехи (конец фазы): тег `phase-2-done`.

### Шаг 0.3. Тестовая инфраструктура и скрипт проверки

**Цель:** одна команда проверяет весь проект. **Зависит от:** 0.2

**Задачи:**

1. Установи GUT в `addons/gut` (если версия не совместима с 4.7 — попробуй gdUnit4; если оба не работают — напиши мини-раннер `tools/run_tests.gd`, который находит `tests/unit/test_*.gd`, вызывает методы `test_*` и считает `assert`-ы; запиши решение в ARCHITECTURE.md).
2. Создай `tools/scene_smoke.gd`: загружает и инстанцирует каждую `.tscn` из `src/` и `tests/`, ловит ошибки загрузки, возвращает ненулевой код при сбое.
3. Создай `tools/check.sh` (и `check.ps1` для Windows).
4. Напиши один тривиальный тест `tests/unit/test_sanity.gd`.

```gdscript
# tools/scene_smoke.gd
extends SceneTree

func _init() -> void:
    var failed: int = 0
    for path in _find_scenes('res://src'):
        var res: Resource = load(path)
        if res == null or not (res is PackedScene):
            printerr('SMOKE FAIL load: ', path)
            failed += 1
            continue
        var inst: Node = (res as PackedScene).instantiate()
        if inst == null:
            printerr('SMOKE FAIL instantiate: ', path)
            failed += 1
        else:
            inst.free()
    print('SMOKE done, failed=', failed)
    quit(1 if failed > 0 else 0)

func _find_scenes(dir_path: String) -> Array[String]:

    for d in da.get_directories():

    for f in da.get_files():
```

```gdscript
# src/player/player_motor.gd
class_name PlayerMotor
extends RefCounted

func simulate(body: CharacterBody3D, inp: PlayerInput, cfg: MovementConfig, stance: int, delta: float) -> void:
    body.rotation.y = inp.yaw
    var local := Vector3(inp.move.x, 0.0, -inp.move.y)
    var wish: Vector3 = body.global_transform.basis * local
    var sprint: bool = inp.pressed(PlayerInput.BTN_SPRINT) and inp.move.y > 0.0
    var target: Vector3 = wish * cfg.speed_for(stance, sprint)
    var v: Vector3 = body.velocity
    if body.is_on_floor():
        v.x = move_toward(v.x, target.x, cfg.accel_ground * delta)
        v.z = move_toward(v.z, target.z, cfg.accel_ground * delta)
        if inp.pressed(PlayerInput.BTN_JUMP) and stance == 0:
            v.y = cfg.jump_velocity
    else:
        v.x = move_toward(v.x, target.x, cfg.accel_air * delta)
        v.z = move_toward(v.z, target.z, cfg.accel_air * delta)
        v.y -= cfg.gravity * delta
    body.velocity = v
    body.move_and_slide()
```

```gdscript
# src/core/health_component.gd
class_name HealthComponent
extends Node

signal health_changed(current: float, max_value: float)
signal damaged(amount: float, source_id: int, zone: int)
signal died(killer_id: int)

@export var max_health: float = 100.0
var current: float = 0.0
var is_dead: bool = false

func _ready() -> void:
    current = max_health

func apply_damage(amount: float, source_id: int = 0, zone: int = 0) -> void:
    if is_dead or amount <= 0.0:
        return
    current = maxf(current - amount, 0.0)
    damaged.emit(amount, source_id, zone)
    health_changed.emit(current, max_health)
    if current <= 0.0:
        is_dead = true
        died.emit(source_id)

func heal(amount: float) -> void:
    if is_dead:
        return
    current = minf(current + amount, max_health)
    health_changed.emit(current, max_health)
```

## ФАЗА 4. СЕТЬ

> Это самая рискованная фаза. Правила: (1) сервер авторитетен, (2) клиент никогда не сообщает «я попал» — только «я нажал огонь», (3) любое сообщение клиента проверяется сервером на допустимость, (4) каждый шаг проверяется интеграционным тестом с **настоящим** сервером и клиентами в отдельных процессах.

### Архитектурные решения сети (внести в ARCHITECTURE.md на шаге 4.1)

| Тема | Решение |
| --- | --- |
| Транспорт | `ENetMultiplayerPeer`, порт 7777 UDP, каналы: 0 — надёжные события, 1 — ввод, 2 — снапшоты, 3 — чат/прочее |
| Тик | Симуляция 60 Гц (`physics_ticks_per_second`), снапшоты клиентам 30 Гц |
| Репликация сущностей | Появление/исчезновение — надёжно (`MultiplayerSpawner` с `spawn_function`). Состояние — **свои компактные снапшоты** (а не `MultiplayerSynchronizer` на каждое свойство), чтобы контролировать трафик для 64 игроков |
| Ввод | Клиент шлёт последние 4–8 вводов каждый тик (избыточность вместо надёжной доставки) |
| Предсказание | Только для своего игрока: предсказание + реконсиляция по подтверждённому тику |
| Чужие игроки | Интерполяция с задержкой 100 мс (≈ 3 снапшота), экстраполяция не более 100 мс |
| Стрельба | Сервер перематывает хитбоксы на время клиента (лаг-компенсация, не более 250 мс) |
| Квантование | Позиция — 16 бит на ось в пределах карты, углы — 16 бит, здоровье — 8 бит |

### Шаг 4.1. Каркас сети: хост, клиент, рукопожатие

**Зависит от:** 3.4g (фаза 3 завершена)

**Задачи:**

1. Расширь автолоад `Net`: `start_server(port, max_clients)`, `join(address, port)`, `disconnect_all()`, сигналы `peer_joined`, `peer_left`, `connected_to_server`, `connection_failed`. Серверный тик `Net.tick` растёт в `_physics_process`.
2. Рукопожатие: клиент после подключения шлёт надёжный RPC `hello(protocol_version, nickname)`; сервер проверяет версию, ник (длина, символы, уникальность), пароль сервера; при несовпадении — `kick(reason)` и отключение.
3. Аргументы командной строки для сервера: `--server --port=7777 --max=32 --map=<id> --password=<x>` (парсер в `Game`, тест парсера).
4. Простое главное меню-заглушка: поля адрес/порт/ник, кнопки Host (listen-server для отладки) и Join.

```gdscript
# src/autoload/net.gd (фрагмент)
extends Node

signal peer_joined(id: int, nickname: String)
signal peer_left(id: int)
signal connected_to_server()
signal connection_failed()

const PROTOCOL_VERSION := 1
const DEFAULT_PORT := 7777

var tick: int = 0
var nicknames: Dictionary = {}  # peer_id -> String

func _physics_process(_delta: float) -> void:
    tick += 1

func start_server(port: int, max_clients: int) -> Error:
    var peer := ENetMultiplayerPeer.new()
    var err: Error = peer.create_server(port, max_clients)
    if err != OK:
        return err
    multiplayer.multiplayer_peer = peer
    multiplayer.peer_connected.connect(_on_peer_connected)
    multiplayer.peer_disconnected.connect(_on_peer_disconnected)
    return OK

func join(address: String, port: int) -> Error:
    var peer := ENetMultiplayerPeer.new()
    var err: Error = peer.create_client(address, port)
    if err != OK:
        return err
    multiplayer.multiplayer_peer = peer
    multiplayer.connected_to_server.connect(func(): connected_to_server.emit())
    multiplayer.connection_failed.connect(func(): connection_failed.emit())
    return OK

@rpc('any_peer', 'call_remote', 'reliable', 0)
func hello(version: int, nickname: String) -> void:
    if not multiplayer.is_server():
        return
    var id: int = multiplayer.get_remote_sender_id()
    if version != PROTOCOL_VERSION or not _valid_nick(nickname):
        _kick(id, 'bad_hello')
        return
    nicknames[id] = nickname
    peer_joined.emit(id, nickname)
```

**Приёмка:** интеграционный тест `tests/integration/test_handshake.gd` запускает сервер и клиента **отдельными процессами** (`OS.create_process`) и проверяет по логам: клиент принят; клиент с неверной версией отклонён. Скрипт `tools/net_test.sh` для ручного запуска сервера + 2 клиентов.

**Не делай:** игроков в сети (4.3).

**Зависит от:** 4.2

### Шаг 4.4. Ввод на сервер и серверная симуляция

**Зависит от:** 4.3

**Задачи:** упаковка `PlayerInput` в `PackedByteArray` (move — 2×int8, yaw/pitch — 2×uint16, buttons — uint16, tick — uint32); клиент каждый тик шлёт пакет из последних N вводов (`@rpc('any_peer','call_remote','unreliable_ordered',1)`); сервер хранит очередь на игрока, берёт **ровно один ввод на тик**; при пустой очереди повторяет последний (не более 5 тиков, затем стоп); отбрасывает вводы из будущего более чем на 1 с и слишком старые; проверяет `move.length() <= 1.01` (защита от «спидхака»). **Приёмка:** серверная позиция игрока совпадает с позицией при локальном прогоне тех же вводов (детерминированный тест мотора).

### Шаг 4.5. Снапшоты и интерполяция чужих игроков

**Зависит от:** 4.4

**Задачи:** сервер раз в 2 тика собирает снапшот: для каждого игрока (позиция, скорость в квантованном виде, yaw, pitch, стойка/флаги, id оружия в руках, `last_processed_input_tick` для владельца) и шлёт каждому клиенту `unreliable_ordered`. Клиент складывает в буфер и рендерит чужих игроков с задержкой 100 мс интерполяцией; при нехватке данных — короткая экстраполяция, затем заморозка. Сглаживание поворота (кватернионы/`lerp_angle`).

```gdscript
# src/net/remote_interpolator.gd (фрагмент)
class_name RemoteInterpolator
extends RefCounted

const INTERP_DELAY_TICKS := 6  # 100 мс при 60 Гц
var _buf: Array[Dictionary] = []  # {tick:int, pos:Vector3, yaw:float, pitch:float, flags:int}

func push(s: Dictionary) -> void:
    _buf.append(s)
    while _buf.size() > 32:
        _buf.pop_front()

func sample(render_tick: float) -> Dictionary:
    var t: float = render_tick - INTERP_DELAY_TICKS
    for i in range(_buf.size() - 1):
        var a: Dictionary = _buf[i]
        var b: Dictionary = _buf[i + 1]
        if t >= a.tick and t <= b.tick:
            var k: float = inverse_lerp(a.tick, b.tick, t)
            return {
                'pos': (a.pos as Vector3).lerp(b.pos, k),
                'yaw': lerp_angle(a.yaw, b.yaw, k),
                'pitch': lerpf(a.pitch, b.pitch, k),
                'flags': a.flags,
            }
    return _buf.back() if not _buf.is_empty() else {}
```

**Приёмка:** юнит-тест интерполятора (дыры в данных, перескок через границу ±π); трафик на клиента при 8 игроках измерен и записан в ARCHITECTURE.md (ожидание < 20 КБ/с).

### Шаг 4.6. Предсказание и реконсиляция своего игрока

**Зависит от:** 4.5

**Идея:** клиент сразу применяет свой ввод (нет задержки управления), а когда приходит снапшот с `last_processed_input_tick = N`, сравнивает серверное состояние на тик N с тем, что он предсказал; при расхождении откатывается к серверному состоянию и **заново проигрывает** все неподтверждённые вводы N+1…текущий.

```gdscript
# src/net/prediction.gd (на клиенте-владельце)
class_name Prediction
extends RefCounted

const BUF := 128
const EPSILON := 0.02  # метры
var inputs: Array = []   # PlayerInput
var states: Array = []   # PredState

func _init() -> void:
    inputs.resize(BUF)
    states.resize(BUF)

func record(tick: int, inp: PlayerInput, st: PredState) -> void:
    inputs[tick % BUF] = inp
    states[tick % BUF] = st

# Возвращает величину визуальной ошибки (для сглаживания камеры)
func reconcile(body: CharacterBody3D, motor: PlayerMotor, cfg: MovementConfig,
        server: PredState, ack_tick: int, now_tick: int, delta: float) -> Vector3:
    var mine: PredState = states[ack_tick % BUF]
    if mine == null or mine.position.distance_to(server.position) < EPSILON:
        return Vector3.ZERO
    var before: Vector3 = body.global_position
    server.apply_to(body)
    for t in range(ack_tick + 1, now_tick + 1):
        var inp: PlayerInput = inputs[t % BUF]
        if inp == null:
            continue
        motor.simulate(body, inp, cfg, server.stance, delta)
        states[t % BUF] = PredState.capture(body)
    return before - body.global_position
```

**Задачи:** `PredState` (позиция, скорость, стойка, флаги on\_floor); код выше; сглаживание визуальной ошибки (камера догоняет за 100 мс, а не телепортируется); при большой ошибке (> 2 м) — жёсткая телепортация. Включить `net_sim` в тестах. Юнит-тест: при идеальной сети реконсиляций ноль; при искусственно изменённом серверном состоянии клиент приходит к серверной траектории.

**Приёмка:** при `net_sim 120 2` управление отзывчивое (🧑), число реконсиляций на тестовом маршруте — в разумных пределах (метрика в overlay), нет «резинки» при ровном беге.

### Шаг 4.7. Сетевая стрельба (сервер решает)

**Зависит от:** 4.6

**Задачи:**

1. Клиент при выстреле шлёт `fire(tick, seed)` (направление берётся сервером из **серверного** `yaw/pitch` на этот тик + разброс по сиду). Локально клиент сразу показывает вспышку/трассер/звук (предсказание косметики), но урон не считает.
2. Сервер: проверяет `can_fire` по **своему** состоянию оружия (патроны, кулдаун в тиках, смена оружия), считает выстрел, формирует `DamageEvent`, применяет к `HealthComponent`.
3. `fire` ограничен по частоте (не чаще, чем позволяет RPM + допуск).
4. Серверные патроны — истина; владельцу шлётся `ammo_sync` для HUD.

**Приёмка:** клиент, меняющий локальные патроны/кулдаун, не получает преимущества (интеграционный тест «читерского» клиента); урон происходит только от серверных решений.

### Шаг 4.8. Лаг-компенсация

**Зависит от:** 4.7

**Задачи:** `LagCompensator` на сервере хранит историю позиций/ориентации/стоек всех игроков за последние 60 тиков. Выстрел клиента несёт `view_tick` (серверное время, которое видел клиент = его оценка серверного тика минус задержка интерполяции). Сервер ограничивает перемотку до 250 мс, переносит хитбоксы на `view_tick`, делает луч, возвращает хитбоксы назад. Перемотка выполняется в одном кадре симуляции, до перемотки и после сохраняются текущие трансформы.

```gdscript
# src/net/lag_compensator.gd (фрагмент)
class_name LagCompensator
extends Node

const HISTORY := 60
const MAX_REWIND_TICKS := 15  # 250 мс
var _frames: Array[Dictionary] = []  # {tick:int, data:{peer_id:{pos,yaw,stance}}}
var _saved: Dictionary = {}

func record(tick: int, players: Dictionary) -> void:
    var data: Dictionary = {}
    for id in players:
        var p: Node3D = players[id]
        data[id] = {'pos': p.global_position, 'yaw': p.rotation.y, 'stance': p.stance}
    _frames.append({'tick': tick, 'data': data})
    while _frames.size() > HISTORY:
        _frames.pop_front()

func rewind(players: Dictionary, now_tick: int, view_tick: int, shooter_id: int) -> void:
    var t: int = maxi(view_tick, now_tick - MAX_REWIND_TICKS)
    var frame: Dictionary = _find(t)
    if frame.is_empty():
        return
    _saved.clear()
    for id in players:
        if id == shooter_id or not frame.data.has(id):
            continue
        var p: Node3D = players[id]
        _saved[id] = p.global_transform
        p.global_position = frame.data[id].pos
        p.rotation.y = frame.data[id].yaw

func restore(players: Dictionary) -> void:
    for id in _saved:
        (players[id] as Node3D).global_transform = _saved[id]
    _saved.clear()
```

**Приёмка:** тест: цель бежит поперёк; клиент с пингом 150 мс целится в видимую цель — попадание засчитывается; при подделанном `view_tick` из далёкого прошлого — ограничение 250 мс срабатывает.

## ФАЗА 5. ИГРОВОЙ РЕЖИМ (CONQUEST)

Вся логика режима живёт **только на сервере**. Клиентам реплицируются результаты: владельцы точек, прогресс, билеты, состояние матча, очки.

### Шаг 5.1. Правила и автомат матча

**Зависит от:** 4.14

**Задачи:** `GameModeRules` (Resource): режим, билеты на команду, время респавна, друзья-огонь (вкл/выкл), реанимация (вкл/выкл), длительность раунда, минимум игроков для старта, множитель bleed. `MatchState` — автомат: `WAITING_FOR_PLAYERS → COUNTDOWN → LIVE → ROUND_END → MAP_VOTE → LOADING`. Переходы только на сервере, состояние реплицируется надёжным RPC при изменении. Юнит-тесты на переходы (например, при падении числа игроков ниже минимума в `COUNTDOWN` возврат в `WAITING_FOR_PLAYERS`).

```gdscript
# src/gamemodes/match_state.gd (фрагмент)
class_name MatchState
extends Node

enum Phase { WAITING, COUNTDOWN, LIVE, ROUND_END, MAP_VOTE, LOADING }
signal phase_changed(new_phase: Phase)

var phase: Phase = Phase.WAITING
var phase_end_tick: int = 0

func set_phase(p: Phase, duration_sec: float = 0.0) -> void:
    assert(multiplayer.is_server())
    phase = p
    phase_end_tick = Net.tick + int(duration_sec * 60.0) if duration_sec > 0.0 else 0
    phase_changed.emit(p)
    _broadcast.rpc(p, phase_end_tick)

@rpc('authority', 'call_remote', 'reliable', 0)
func _broadcast(p: int, end_tick: int) -> void:
    phase = p as Phase
    phase_end_tick = end_tick
    phase_changed.emit(phase)
```

**Приёмка:** тесты автомата; на сервере с двумя клиентами матч стартует по таймеру.

### Шаг 5.2. Команды

**Зависит от:** 5.1

**Задачи:** две команды (0 и 1), цвета и названия во фракционном ресурсе `FactionData`; автобаланс при входе (в меньшую команду), запрет перекоса > 2 игрока; смена команды только в `WAITING` или по правилам; различение друг/враг (ники над головой — только у союзников, красные маркеры у засвеченных врагов). Тесты балансировщика.

**Приёмка:** 10 условных подключений распределяются 5/5.

### Шаг 5.3. Система возрождения

**Зависит от:** 5.2

**Задачи:** типы точек: база (всегда доступна), захваченный флаг, отряд (рядом с сокомандником), маяк. Сервер выбирает **безопасную позицию** в зоне точки через оценочную функцию; запрещает спавн, если враг ближе 15 м или видит точку; неуязвимость 2 с (снимается при стрельбе). UI выбора точки на карте (в 11.x), пока выбор — консольной командой `spawn <point_id>`.

```gdscript
# src/gamemodes/spawn_scoring.gd
class_name SpawnScoring
extends RefCounted

const MIN_ENEMY_DIST := 15.0

static func score(pos: Vector3, friends: Array[Vector3], enemies: Array[Vector3]) -> float:
    var nearest: float = INF
    for e in enemies:
        nearest = minf(nearest, pos.distance_to(e))
    if nearest < MIN_ENEMY_DIST:
        return -INF
    var s: float = minf(nearest, 80.0)
    for f in friends:
        if pos.distance_to(f) < 40.0:
            s += 5.0
    return s
```

**Приёмка:** тесты оценщика (враг рядом → точка отвергнута); спавн никогда не происходит внутри геометрии (проверка пустоты капсулы через `test_move`/`PhysicsShapeQueryParameters3D`).

### Шаг 5.4. Точки захвата

**Зависит от:** 5.3

**Идея:** контроль точки — число `control` ∈ \[−1, +1\]: +1 — полностью у команды 0, −1 — у команды 1. Перевес игроков двигает значение; при равенстве точка «оспаривается» и не меняется. Чужую точку сначала нейтрализуют (переход через 0), затем захватывают.

```gdscript
# src/gamemodes/conquest/capture_point.gd
class_name CapturePoint
extends Area3D

signal owner_changed(point_id: StringName, new_owner: int)

@export var point_id: StringName
@export var capture_time: float = 20.0
@export var max_rate_players: int = 4

var counts: Array[int] = [0, 0]
var control: float = 0.0
var owner_team: int = -1  # -1 нейтральная

func server_tick(delta: float) -> void:
    var diff: int = counts[0] - counts[1]
    if diff == 0:
        return
    var rate: float = float(mini(absi(diff), max_rate_players)) / capture_time
    control = clampf(control + signf(diff) * rate * delta, -1.0, 1.0)
    _update_owner()

func _update_owner() -> void:
    var new_owner: int = owner_team
    if control >= 1.0:
        new_owner = 0
    elif control <= -1.0:
        new_owner = 1
    elif owner_team == 0 and control <= 0.0:
        new_owner = -1
    elif owner_team == 1 and control >= 0.0:
        new_owner = -1
    if new_owner != owner_team:
        owner_team = new_owner
        owner_changed.emit(point_id, owner_team)
```

**Задачи:** код выше + подсчёт `counts` по живым игрокам в зоне (`body_entered/exited` по слою `players`, мёртвые и DOWNED не считаются); репликация `control` и `owner_team` клиентам (снапшот 5 Гц достаточно); визуал — флагшток/цвет/кольцо на земле. Тесты: 1 vs 0 — захват за `capture_time`; 2 vs 2 — без изменений; чужая точка нейтрализуется до захвата.

**Приёмка:** тесты зелёные; на тестовой сцене с 2 клиентами флаг переходит из рук в руки (🧑).

### Шаг 5.5. Билеты и условия победы

**Зависит от:** 5.4

**Задачи:** у каждой команды N билетов (по умолчанию 300). Смерть игрока → −1 билет своей команды. **Bleed**: если команда А контролирует больше половины точек, команда Б теряет `bleed_rate × (flags_A − N/2)` билетов в секунду (`bleed_rate` из правил, старт 0.5). Победа: у соперника 0 билетов, либо по истечении времени — у кого больше билетов. Ничья обрабатывается правилом «овертайм 60 с». `TicketService` — чистая логика, без узлов; юнит-тесты на формулы (5 точек: 3/2 → bleed; 5/0 → максимальный).

**Приёмка:** тесты; при симуляции на 10 минут без игроков одна команда с 3 флагами выигрывает по bleed.

## ФАЗА 6. КАРТЫ

### Принципы карт для BattleBit/Battlefield-подобной игры

- Размер: 800–1500 м по большой стороне, 5–7 точек, две базы на противоположных краях.
- Три «полосы» (левая — город/укрытия, центр — открытые дистанции/техника, правая — лес/холмы), 2–3 перехода между ними.
- Укрытие каждые 10–15 м, дальность прямой видимости на открытых местах не более \~300 м.
- На каждой точке: 1–2 здания для ближнего боя, 2 подхода, укрытия для снайпера на удалении 80–150 м.
- Маршруты для техники шире 6 м, пешеходные обходы вокруг.
- Все метры — реальные; геометрия на сером уровне проверяется 🧑 человеком до наполнения.

### Шаг 6.1. MapData и загрузчик карт

**Зависит от:** 5.11

**Задачи:** `MapData` (Resource): `id`, название, путь к сцене, поддерживаемые режимы, число игроков (мин/рек/макс), размер, миникарта, список точек, границы. `MapLoader.load_map(id)` загружает, проверяет наличие обязательных узлов (`SpawnPoints`, `CapturePoints`, `Bounds`, `NavRegion`) и выдаёт список ошибок. Тест на валидатор карты.

**Приёмка:** тестовая карта (серый полигон) проходит валидацию.

### Шаг 6.2. Ландшафт

**Зависит от:** 6.1

**Задачи:** собственный генератор рельефа `tools/gen_terrain.gd`: карта высот (шум + ручные маски: ровные площадки под базы/точки, дороги, русла), экспорт в `.res`/`.png`. `TerrainChunk` — сетка 64×64 м, шаг 2 м, `ArrayMesh` + `HeightMapShape3D`/`ConcavePolygonShape3D` для коллизии, 3 уровня детализации с переключением по расстоянию, швы без дыр. Шейдер: смешивание 3–4 материалов по высоте/уклону (трава, грунт, камень, песок), triplanar по склонам. Если принято решение использовать Terrain3D (ADR) — вынести интеграцию в этот шаг и убедиться в совместимости с 4.7 и с выделенным сервером.

**Приёмка:** карта 1000×1000 м генерируется скриптом headless за разумное время; игрок ходит по рельефу без проваливаний; тест на непрерывность высот на стыках чанков.

### Шаг 6.3. Растительность и мелкие объекты

**Зависит от:** 6.2

**Задачи:** деревья, кусты, трава, камни — `MultiMeshInstance3D`, раскладка скриптом по маскам (плотность по биомам), `visibility_range_*` и LOD, коллизия только у стволов (капсулы). ### Шаг 6.4. Модульные здания

### Шаг 7.2. Библиотека процедурных мешей `MeshBuilder`

**Зависит от:** 7.1

**Задачи:** класс `MeshBuilder` (SurfaceTool): `add_box`, `add_bevel_box` (фаска 2 мм–5 см), `add_cylinder`, `add_wedge`, `add_cone`, `add_extrude(polygon_2d, height)`, `mirror_x()`, `translate/rotate/scale` для частей, цвет на деталь, `build() -> ArrayMesh`, `build_collision_convex()`. Плоское затенение через `set_smooth_group(-1)`. **Обязательные тесты:** число вершин, габариты (AABB), нормали всех граней направлены наружу (для каждой грани куба скалярное произведение нормали и направления от центра > 0).

```gdscript
# src/fx/mesh_builder.gd (ядро)
class_name MeshBuilder
extends RefCounted

# Индексы углов: bit0 = x, bit1 = y, bit2 = z (0 = минус, 1 = плюс)
# Грани перечислены по часовой стрелке при взгляде снаружи (так в Godot задаётся лицевая сторона).
const BOX_FACES: Array = [
    [4, 6, 7, 5],  # +Z
    [1, 3, 2, 0],  # -Z
    [5, 7, 3, 1],  # +X
    [0, 2, 6, 4],  # -X
    [2, 3, 7, 6],  # +Y
    [0, 4, 5, 1],  # -Y
]

var _st := SurfaceTool.new()

func _init() -> void:
    _st.begin(Mesh.PRIMITIVE_TRIANGLES)
    _st.set_smooth_group(-1)

func add_box(center: Vector3, size: Vector3, color: Color) -> void:
    var h: Vector3 = size * 0.5
    var c: Array[Vector3] = []
    for i in 8:
        c.append(center + Vector3(
            h.x if (i & 1) != 0 else -h.x,
            h.y if (i & 2) != 0 else -h.y,
            h.z if (i & 4) != 0 else -h.z))
    for f in BOX_FACES:
        _quad(c[f[0]], c[f[1]], c[f[2]], c[f[3]], color)

func _quad(a: Vector3, b: Vector3, c: Vector3, d: Vector3, color: Color) -> void:
    for p in [a, b, c, a, c, d]:
        _st.set_color(color)
        _st.add_vertex(p)

func build() -> ArrayMesh:
    _st.generate_normals()
    return _st.commit()
```

**Приёмка:** тесты нормалей и габаритов зелёные; тестовая сцена показывает куб, цилиндр, клин правильно освещёнными (скриншот или 🧑).

```gdscript
# tools/gen_sfx.gd (фрагмент)
static func noise_burst(duration: float, decay: float, rate: int = 22050) -> AudioStreamWAV:
    var n: int = int(duration * rate)
    var data := PackedByteArray()
    data.resize(n * 2)
    var rng := RandomNumberGenerator.new()
    rng.seed = 12345
    for i in n:
        var t: float = float(i) / rate
        var amp: float = exp(-t * decay)
        var s: int = int(clampf(rng.randf_range(-1.0, 1.0) * amp, -1.0, 1.0) * 32767.0)
        data.encode_s16(i * 2, s)
    var w := AudioStreamWAV.new()
    w.format = AudioStreamWAV.FORMAT_16_BITS
    w.mix_rate = rate
    w.stereo = false
    w.data = data
    return w
```

**Приёмка:** все события из списка имеют звук; пул 3D-звуков не превышает лимит (тест); 🧑 микс не клиппит (выстрел + взрыв + шаги одновременно).

## ФАЗА 9. РАЗРУШАЕМОСТЬ И ФИЗИКА

Честное ограничение: вокселей уровня BattleBit в Godot «из коробки» нет. План даёт **предфрактурное разрушение** стен/заборов/укрытий и кратеры-декали; воксельный ландшафт — вне рамок (отдельный большой проект).

### Шаг 9.1. Компонент разрушаемости

**Зависит от:** 8.9

**Задачи:** `DestructibleComponent`: HP, состояния (целый → повреждён → разрушен), типы урона с множителями (пули почти не ломают бетон, взрывчатка ломает), `destroyed` сигнал. Сервер решает; клиентам уходит надёжное событие `destroyed(object_id, seed, hit_point, impulse)`. Новые игроки при подключении получают список уже разрушенных объектов.

**Приёмка:** тесты уровней урона; позднее подключение видит те же разрушения.

### Шаг 9.2. Разрушаемые стены и здания

**Зависит от:** 9.1, 6.4

**Задачи:** сегмент стены — отдельный узел с заранее нарезанными на N кусков мешами; при разрушении сегмент скрывается, коллизия отключается (проём!), клиент по `seed` создаёт обломки (RigidBody3D на слое `debris`, не сталкиваются с игроками), живут 8–12 с и возвращаются в пул, общий лимит 150–300. Опорные конструкции: потеря опоры → обрушение перекрытия (упрощённо: граф зависимостей сегментов, проверка на сервере). Пыль и звук.

**Приёмка:** граната пробивает стену дома, игрок проходит в проём; лимит обломков соблюдается (тест на счётчик).

### Шаг 9.3. Навигация и разрушения

**Зависит от:** 9.2

**Задачи:** после разрушения — обновление навмеша локально (динамические `NavigationObstacle3D`/`NavigationLink3D` для проёмов, либо повторный локальный запекание региона) — выбрать вариант по замерам. Боты не должны застревать в проёмах.

**Приёмка:** автотест: после разрушения стены бот находит маршрут через проём или обходит.

### Шаг 9.4. Кратеры и следы взрывов

**Зависит от:** 2.10

**Задачи:** декали обугливания и воронок (пул), дым, осколки в воздухе (частицы), снос растительности в радиусе (скрытие экземпляров MultiMesh по индексам, серверный список), встряска камеры с затуханием по расстоянию.

**Приёмка:** FPS не падает ниже бюджета при серии из 10 взрывов за 5 с.

### Шаг 9.5. Рэгдоллы

**Зависит от:** 7.6

**Задачи:** для сегментного персонажа — при смерти заменить части на `RigidBody3D` с `ConeTwistJoint3D`/`Generic6DOFJoint3D` (проверить поведение с Jolt), стартовый импульс от направления попадания и типа оружия, время жизни 8 с, не более 8 одновременных (самый старый исчезает), только клиент (сервер не симулирует). Реанимируемый (DOWNED) — не рэгдолл, а лежащая поза.

**Приёмка:** на 3 клиентах рэгдоллы визуально отличаются, но не влияют на игру; лимит соблюдается.

### Шаг 9.6. Физические предметы

**Зависит от:** 9.1

**Задачи:** чисто косметические двигаемые предметы (бочки, коробки) — клиентская физика, без репликации; важные (взрывоопасные бочки) — серверное событие.

**Приёмка:** синхронизации нет, трафик не вырос.

**Конец фазы 9:** `phase-9-done`.

## ФАЗА 10. БОТЫ

**Ключевая идея:** бот — это «клиент без сети». Его мозг каждый тик производит обычный `PlayerInput`, а дальше работают те же `PlayerMotor`, оружие и урон, что и у людей. Никаких отдельных «ботовских» правил боя. Боты живут только на сервере.

### Шаг 10.1. Каркас бота

**Зависит от:** 9.6

**Задачи:** `BotBrain` (Node) с методом `think(delta) -> PlayerInput`; `BotController` создаёт серверную сущность игрока с отрицательным/служебным `peer_id`, регистрирует её в командах, счёте, отрядах как обычного игрока (флаг `is_bot`). Серверная очередь ввода заменяется вызовом мозга. Имена из списка, отображаются с пометкой \[BOT\] (настройка).

```gdscript
# src/ai/bot_brain.gd (каркас)
class_name BotBrain
extends Node

enum State { IDLE, MOVE_TO_OBJECTIVE, ENGAGE, TAKE_COVER, RELOAD, HEAL_REVIVE, RETREAT }

var state: State = State.IDLE
var difficulty: BotDifficulty  # Resource: reaction_time, aim_error_deg, burst_len, memory_sec
var target_id: int = -1
var _think_accum: float = 0.0
var _cached: PlayerInput = PlayerInput.new()

func produce_input(delta: float) -> PlayerInput:
    _think_accum += delta
    if _think_accum >= 0.1:  # мозг думает 10 раз/с, движение — каждый тик
        _think_accum = 0.0
        _think()
    return _cached

func _think() -> void:
    pass  # заполняется в шагах 10.2–10.5
```

**Приёмка:** бот появляется на сервере, стоит и отображается у клиентов как игрок; в списке игроков помечен.

### Шаг 10.2. Передвижение по навмешу

**Зависит от:** 10.1, 6.7

**Задачи:** `NavigationAgent3D` → ближайшая точка пути → `move`-вектор и `yaw`. Детектор застревания (скорость < 0.3 м/с при активном пути > 2 с → прыжок/смена пути/перебор альтернатив). Бег/шаг по ситуации; переход в присед/лёжа на позиции огня; обход друг друга (avoidance). Прыжок/залезание по `NavigationLink3D`.

**Приёмка:** бот проходит от базы A до точки в центре карты и до базы B без застреваний в 20 запусках (автотест с сидами).

### Шаг 10.3. Восприятие

**Зависит от:** 10.2

**Задачи:** зрение (конус 110°, дальность по освещению/типу, проверка линии луча с бюджетом N лучей на тик — по кругу), слух (события выстрелов/взрывов/шагов с радиусом), память (последняя известная позиция врага, `memory_sec`), приоритеты целей (близость, угроза, кто стреляет в бота). Используется спотирование (`spot`) союзников.

**Приёмка:** бот замечает врага на открытой местности на ожидаемой дальности; не видит сквозь стены (тест); бюджет лучей не превышен.

### Шаг 10.4. Бой

**Зависит от:** 10.3

**Задачи:** реакция (`reaction_time`), наведение с ошибкой (`aim_error_deg`, уменьшается со временем фокуса, отдача учитывается), стрельба очередями по расстоянию, перезарядка в безопасный момент, использование гранат по укрытым целям, отступление при HP < 30%, укрытия: выбор точки укрытия по карте `CoverPoint` (Marker3D в сцене карты) либо по вычислению (отсутствие LOS до врага, близость). Уровни сложности: Рекрут / Солдат / Ветеран / Элита — ресурсы `.tres`.

**Приёмка:** симуляция «бот vs бот» на полигоне: TTK и точность в диапазонах из `BotDifficulty` (тест статистики на 200 дуэлей).

### Шаг 10.5. Цели режима и роли классов

**Зависит от:** 10.4, 5.5

**Задачи:** `BotCommander` на сервере распределяет ботов по точкам (ближайшая нейтральная/вражеская, оборона, балансировка 60/40 атака/защита); поведение по классам: Medic — лечит/реанимирует, Support — раскладывает ящики и подавляет, Engineer — чинит технику/ставит мины, Recon — занимает позиции и засвечивает, Assault — прорыв. Боты присоединяются к отрядам.

**Приёмка:** на карте 1 боты захватывают и удерживают точки; один матч команда ботов против команды ботов доходит до конца за ≤ 20 минут.

### Шаг 10.6. Боты и техника

**Зависит от:** 10.5, 8.8

**Задачи:** водитель по дорожному графу (`RoadPath` в карте) с торможением на поворотах, стрелок-бот атакует цели, пассажиры занимают места; ограничение: боты не водят вертолёт (опционально).

**Приёмка:** джип с ботом-водителем и ботом-стрелком доезжает до точки и не переворачивается в 10 запусках из 10.

### Шаг 10.7. Заполнение серверов

**Зависит от:** 10.5

**Задачи:** `BotFill`: целевое число игроков N; когда заходит человек — удаляется самый «лишний» бот; при выходе — добавляется; приоритет балансировки команд; CLI `--bots=<n>`, `--bot-difficulty=<id>`. Снижение стоимости: боты, не видимые игрокам и далеко от них, думают реже (до 2 Гц).

**Приёмка:** при 8 людях + 24 ботах сервер держит бюджет тика (см. 13.1).

### Шаг 10.8. Режим тренировки (офлайн)

**Зависит от:** 10.7

**Задачи:** кнопка «Тренировка»: запускает локальный сервер (listen) в том же процессе + ботов, без сети наружу (`bind 127.0.0.1`). Выбор карты, режима, сложности, числа ботов.

**Приёмка:** новый игрок за 3 клика попадает в матч с ботами.

### Шаг 10.9. Автоматические матчи ботов

**Зависит от:** 10.8

**Задачи:** `tools/bot_match.gd` — headless матч «бот vs бот» на 10 игровых минут с отчётом: убийства, захваты, застревания (≥ 10 с без прогресса), среднее время тика, утечки узлов. Используется как ночная регрессия.

**Приёмка:** 3 запуска подряд без падений; отчёт сохраняется в `docs/BOT_REPORT.md`.

**Конец фазы 10:** `phase-10-done`. 🧑 Поиграть против ботов 15 минут на каждой сложности.

**Задачи:** формула уровня (`xp_for_level(n)`, кривая в `.tres`), начисление опыта из `ScoreService` по итогам матча и во время (всплывающие «+100»); опыт по классу и по оружию. Тесты на кривую (монотонность, отсутствие переполнения).

**Приёмка:** после матча профиль обновляется и показывается на экране итогов.

### Шаг 12.3. Разблокировки

**Зависит от:** 12.2

**Задачи:** дерево разблокировок (`UnlockTree` Resource): оружие, обвесы, гаджеты, косметика; требования (ранг/опыт класса/выполнение задания). Серверная проверка: клиент не может выбрать оружие, которое у него не открыто (в сообщении лодаута сервер сверяет с профилем, который хранится на сервере по UUID).

**Приёмка:** новый профиль имеет базовый набор; попытка взять закрытое оружие отклоняется сервером (интеграционный тест).

### Шаг 12.4. Серверное хранение профилей

Идентификация по UUID + секретному токену, выданному при первом входе. Предупреждение в документации: без центрального бэкенда профили привязаны к серверу. ## ФАЗА 13. ОПТИМИЗАЦИЯ И МАСШТАБ (32 → 64 → больше)

> Правило: **сначала измерить, потом оптимизировать**. Любой шаг начинается с замера «до» и заканчивается замером «после» в `docs/PERF.md`. Оптимизация без цифр запрещена.

### Бюджеты (фиксируются на шаге 13.1)

| Метрика | Цель |
| --- | --- |
| Клиент, 1080p, пресет Medium, 64 игрока | ≥ 60 FPS на средней видеокарте (класс GTX 1660 / RX 580) |
| Сервер, 64 игрока | время одного тика симуляции ≤ 8 мс (запас до 16.7 мс) |
| Трафик сервер → клиент | ≤ 64 КБ/с на клиента |
| Трафик клиент → сервер | ≤ 8 КБ/с |
| Память клиента | ≤ 3 ГБ, сервера ≤ 1.5 ГБ |
| Время загрузки карты | ≤ 20 с на SSD |

### Шаг 13.1. Бенчмарк и базовые замеры

**Зависит от:** 12.5

**Задачи:** `tools/bench.gd`: сервер с N ботами (8/32/64), скриптованные клиенты-наблюдатели; сбор `Performance.get_monitor(...)` (кадр, физика, объекты, draw calls), время тика по подсистемам (собственные метки `Profiler.begin('lag_comp')`), трафик. Результаты → `docs/PERF.md` таблицей; скрипт возвращает код ошибки, если бюджет превышен (будет использоваться в CI).

**Приёмка:** первая таблица замеров на 8/32/64 ботах; узкие места названы по именам подсистем.

### Шаг 13.2. Оптимизация сервера

**Зависит от:** 13.1

**Задачи (в порядке выгоды, каждая — отдельный коммит с замером):**

1. Сервер использует **упрощённую позу**: хитбоксы по стойке и углу прицеливания без `AnimationTree` и визуальных узлов (визуал вообще не создаётся при `dedicated_server`).
2. Отключить `_process` во всех узлах сервера, где он не нужен; логику вести в одном месте (`ServerTick`), порядок систем фиксирован.
3. Пространственный хэш (сетка 32 м) для запросов «кто рядом» (захват точек, лечение, интерес, звуки).
4. Лучи стрельбы — ограничить число одновременных за тик, кэшировать запрос параметров (`PhysicsRayQueryParameters3D` переиспользуется).
5. Боты думают по расписанию (10.7), вне зоны видимости людей — реже.
6. Сборка снапшотов в предвыделенные `PackedByteArray`, без создания словарей на каждый тик.
7. Если после всего выше узкое место остаётся (сериализация/лаг-комп), вынести его в GDExtension (C++) — **только после** доказательства замером и с записью ADR.

**Приёмка:** сервер на 64 игроках укладывается в бюджет тика (цифры в PERF.md).

### Шаг 13.3. Оптимизация сети

**Зависит от:** 13.2

**Задачи:**

1. **Интерес-менеджмент:** игрок получает полные данные об игроках в радиусе 150 м (30 Гц), 150–400 м — 10 Гц, дальше 400 м — не получает (кроме спотированных и членов отряда). Радиусы — в `server.cfg`.
2. Дельта-сжатие: поле передаётся только при изменении по сравнению с последним подтверждённым клиентом снапшотом (бит-маска изменённых полей).
3. Битовая упаковка (квантование + `BitWriter`), один пакет на клиента на снапшот; ограничение размера пакета (MTU ≈ 1200 байт) — большие данные дробятся по приоритету.
4. Аккумулятор приоритетов: близкие/стреляющие/движущиеся быстро получают данные чаще; общий потолок байт/с на клиента.
5. Проверить опции ENet-хоста (сжатие, лимиты каналов) в актуальном API 4.7.

**Приёмка:** на 64 игроках трафик ≤ бюджета; визуально нет рывков у игроков на 200 м (🧑).

### Шаг 13.4. Оптимизация рендеринга

**Зависит от:** 13.1

**Задачи:** запечённый occlusion culling (`OccluderInstance3D`) для зданий/холмов; `visibility_range` + HLOD для зданий и техники; LOD мешей (автогенерация при импорте, либо собственные упрощённые версии из `MeshBuilder`); дальность и каскады теней; ограничение числа динамических источников света (вспышки — без теней); один материал = слияние вызовов отрисовки; сжатие текстур VRAM; MultiMesh для растительности и мелкого реквизита; лимиты частиц и декалей; масштабирование 3D-разрешения (FSR/масштаб в настройках). Таблица «что включает пресет» в PERF.md.

**Приёмка:** draw calls и треугольники на сцене с видом на середину карты ниже бюджета; пресет Low ≥ 60 FPS на слабой конфигурации.

### Шаг 13.5. Оптимизация клиента (CPU)

**Зависит от:** 13.4

**Задачи:** анимационный LOD (дальние игроки обновляются реже/без IK), отключение `process` у скрытых и дальних объектов, пулы эффектов (проверка), никаких аллокаций в горячих путях (профайлер GC/аллокаций), `Thread`-ы только там, где безопасно (загрузка ресурсов, запекание), строки как `StringName`.

**Приёмка:** CPU-кадр клиента на 64 игроках ниже бюджета; в PERF.md есть топ-10 затрат.

### Шаг 13.6. Загрузка и память

**Зависит от:** 13.4

**Задачи:** фоновая загрузка карт и ресурсов (`ResourceLoader.load_threaded_request`), экран загрузки с прогрессом, выгрузка при смене карты (проверка утечек: 5 смен подряд → память возвращается к базе ±5%), лимиты кеша.

**Приёмка:** замер времени загрузки и памяти; тест смены карт проходит.

### Шаг 13.7. Решение о масштабе 128/254

**Зависит от:** 13.3

**Задачи:** эксперимент (не реализация): сервер с 128 и 254 ботами; где ломается (тик, трафик, физика); варианты — C++ для горячих путей, упрощение физики для далёких игроков, тик 30 Гц, шардинг по зонам. Итог — ADR «Что делаем для >64» с цифрами; решение принимает человек 🧑.

**Приёмка:** отчёт с цифрами и рекомендацией.

### Шаг 13.8. Регрессия производительности

**Зависит от:** 13.2

**Задачи:** `tools/bench.sh` в CI/ночном запуске: падает, если время тика сервера, трафик или память превышают бюджет более чем на 15%.

**Приёмка:** искусственная деградация (добавленный `OS.delay_msec`) ловится бенчмарком.

**Конец фазы 13:** `phase-13-done`.

## ФАЗА 14. БЕЗОПАСНОСТЬ И АДМИНИСТРИРОВАНИЕ

Честно: **полного античита на стороне клиента в Godot нет**. Стратегия — архитектурная: сервер авторитетен, клиенту не доверяется ничего, подозрительное логируется для администратора. Интеграция коммерческих античитов (EAC/BattlEye) — вне плана.

### Шаг 14.1. Модель угроз

**Зависит от:** 13.8

**Задачи:** `docs/THREATS.md`: speedhack, teleport, aimbot, wallhack (информационный), rapid-fire, дублирование предметов, RPC-флуд, DoS, подмена владельца, чтение приватных данных, подбор пароля админа. Для каждой — механизм защиты и где проверяется.

**Приёмка:** документ создан, каждому пункту сопоставлен тест в 14.3/14.8.

### Шаг 14.2. Укрепление RPC

**Зависит от:** 14.1

**Задачи:** аудит скриптом `tools/audit_rpc.gd` — список всех `@rpc`, режимы, проверки. Правила: любой `any_peer` RPC (1) проверяет `multiplayer.get_remote_sender_id()` и состояние отправителя (жив ли, есть ли право), (2) валидирует типы и диапазоны аргументов (NaN/Inf, длины строк и массивов), (3) имеет **лимит частоты** на пир (`RateLimiter` с токен-бакетом), (4) не меняет игровое состояние, а лишь создаёт запрос. При нарушении: счётчик подозрений → предупреждение → кик.

**Приёмка:** аудит-скрипт показывает 100% RPC с проверками; тест на спам (1000 вызовов/с) — сервер не деградирует, нарушитель кикается.

### Шаг 14.3. Серверные проверки правил

**Зависит от:** 14.2

**Задачи:** движение (макс. скорость × допуск; при превышении — коррекция + счётчик), «телепорт» (дельта позиции за тик), стрельба (скорострельность, патроны, смена оружия, угол/дальность), гаджеты (владение, заряды, дистанция установки), техника (только место водителя управляет), возрождение (только разрешённые точки), смена класса (только в безопасное время), реанимация (дистанция).

**Приёмка:** набор «читерских» клиентов `tests/security/*` (скриптами подменяющих ввод) не получает преимущества: каждый случай даёт отказ/коррекцию/кик.

### Шаг 14.4. Скрытие информации

**Зависит от:** 14.3, 13.3

**Задачи:** мёртвым/наблюдателям не отправляются позиции вражеской команды; враги вне радиуса интереса не отправляются (13.3); приватные данные (патроны, лодаут чужих) не покидают сервер; позиции спотированных врагов отправляются на время засветки. Простая серверная проверка видимости для маркеров (луч от союзника до врага), с бюджетом.

**Приёмка:** сетевой анализ: клиент не получает позиций неспотированных удалённых врагов (тест, перехватывающий снапшоты).

### Шаг 14.5. Журналы и статистические флаги

**Зависит от:** 14.3

**Задачи:** `SuspicionLog`: аномальные метрики на игрока (процент хедшотов, скорость поворота прицела перед выстрелом, время реакции, точность в движении, число отказанных выстрелов). Записи в `logs/suspicion.jsonl` с метками времени — **без автоматического бана** (только пометка для администратора). Ротация логов.

**Приёмка:** симулированный «аимбот» (идеальное наведение за 1 кадр) помечается; обычный бот сложности «Элита» — нет (тест порогов).

### Шаг 14.6. Административный интерфейс

**Зависит от:** 14.2

**Задачи:** удалённая консоль (TCP/WebSocket только на `127.0.0.1` по умолчанию; наружу — с TLS/паролем): `status`, `players`, `kick`, `ban`, `unban`, `map`, `say`, `bots`, `restart_round`, `reload_config`. Бан-лист в файле (IP + UUID). Аутентификация — пароль из `server.cfg`, задержка при неверных попытках. Метрики в `logs/metrics.json` раз в 10 с (игроки, тик, трафик).

**Приёмка:** тесты команд; неверный пароль 5 раз → временная блокировка адреса.

### Шаг 14.7. Защита от перегрузки

**Зависит от:** 14.2

**Задачи:** лимит подключений с одного IP, тайм-аут рукопожатия (5 с), лимит размера пакетов и числа RPC в секунду, защита от «зомби-слотов», ограничение скорости загрузки данных новым игрокам. Документ `docs/HOSTING.md` с рекомендациями по фаерволу (UDP-порт), лимитам ОС и мониторингу.

**Приёмка:** нагрузочный тест: 100 «пустых» подключений за секунду не мешают играющим.

### Шаг 14.8. Фазз-тесты

**Зависит от:** 14.7

**Задачи:** `tests/security/fuzz_rpc.gd` — случайные/экстремальные аргументы (NaN, огромные массивы, отрицательные индексы, пустые строки) во все RPC; сервер не падает и не зависает.

**Приёмка:** 10 000 итераций без падения; утечек нет.

**Конец фазы 14:** `phase-14-done`.

## ПРИЛОЖЕНИЕ B. Если агент ведёт себя неправильно

| Симптом | Что делать |
| --- | --- |

| Пишет сразу несколько шагов | Откатить на тег предыдущего шага (`git reset --hard step-N.M`), повторить с командой «только шаг N.M» |
| Заявляет «готово» без тестов | Потребуйте вывод `tools/check.sh` и пункты приёмки с отметками (Правило 19) |
| Раздувает файлы | Правило 9: разбить на компоненты, выполнить отдельным шагом-рефакторингом `R.N` |
| Меняет архитектуру втихую | Любое такое изменение — только через запись в ARCHITECTURE.md и подтверждение человека |
| Застрял на ошибке 3+ итерации | Остановка по Правилу 15: BLOCKERS.md с вариантами, решение за человеком |
| Теряет контекст на длинной сессии | Приложение A «Сжатие контекста», новая сессия, чтение AGENTS.md/PROGRESS.md |
| Добавляет внешние ассеты без лицензии | Откат файла; запись в ASSETS.md обязательна до коммита |
