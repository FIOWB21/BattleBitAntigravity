# ARCHITECTURE

## Решения (ADR)

| Область | Решение | Комментарий |
| --- | --- | --- |
| Движок | Godot `4.7.2.stable.official.ed1daf0bf` (standard build, не .NET) | Проверено через `$GODOT --version` на шаге 0.1 |
| Язык | GDScript (строгая типизация) | C++/GDExtension только для доказанных узких мест (Фаза 13) |
| Рендер | Forward+ (`forward_plus`) для ПК | Опции Mobile/Compatibility не поддерживаются |
| Физика | Jolt Physics (`Jolt Physics`) | Настроено в `physics/3d/physics_engine` |
| Тик физики | 60 Гц | Сетевая отправка состояния 30 Гц |
| Сглаживание камеры и физики | `physics/common/physics_interpolation=true`, `Camera3D` в режиме `PHYSICS_INTERPOLATION_MODE_OFF` | `Player` и `Head` интерполируются движком на 60 Гц, а `Camera3D` обновляется в `_process` по `head.get_global_transform_interpolated().origin` + покадровым `yaw`/`pitch` и `CameraEffects`, исключая конфликт тиковой интерполяции с обзором мыши на 144+ FPS |
| Сеть | `ENetMultiplayerPeer` (UDP), High-level Multiplayer API, свой слой предсказания | Без сторонних сетевых аддонов |
| Модель авторитета | Сервер решает всё: урон, смерти, захват, спавн | Клиент отправляет только ввод (`PlayerInput`) |
| Стрельба | Hitscan (серверный, с компенсацией лага) для винтовок/пистолетов; снаряды для гранат/ракет/танка | |
| Данные | `Resource` (`.tres`) для оружия, классов, карт, режимов | Никаких магических чисел в логике |
| Тесты | Собственный мини-раннер `tools/run_tests.gd` + базовый класс `GutTest` (`addons/gut/test.gd`) и обёртка `addons/gut/gut_cmdln.gd` | Полная совместимость с Godot 4.7.2 (`Logger`), строгая типизация, поддержка `assert_*` и встроенного `assert()` |
| Террейн | Свой чанковый heightmap-меш | Terrain3D — только при подтверждённой совместимости с 4.7 |
| Персонаж | `Skeleton3D` + `AnimationTree`, анимации CC0 | Лицензии фиксируются в `ASSETS.md` |
| Боты | `NavigationServer3D` + конечный автомат | Фаза 10 |
| Хранилище | `ConfigFile`/JSON локально | Бэкенд-аккаунты — вне MVP |

## Отладочный оверлей и консоль

- **`DebugOverlay` (`res://src/ui/debug_overlay.tscn`, `res://src/ui/debug_overlay.gd`)** — слой `CanvasLayer` с панелью телеметрии `StatsPanel` (FPS, кадр в мс, память в MiB, число узлов, позиция локального игрока и пинг из `Game.debug`, переключение по `F3`) и панелью консоли `ConsolePanel` (переключение по `` ` `` / `KEY_QUOTELEFT`).
- **`DebugConsole` (`res://src/ui/debug_console.gd`)** — `RefCounted`-реестр и парсер команд (`commands: Dictionary` вида `name -> Callable`), предоставляющий встроенные команды `help`, `fps <n>`, `net_sim <ping_ms> <loss_%>`, `god`, `noclip`, `damage <n>` (отладочный локальный урон: `damage_target` → `Game.debug["local_health_component"]` → `HealthComponent` узла `Player`).

## HUD

- **`HUD` (`res://src/ui/hud/hud.tscn`, `res://src/ui/hud/hud.gd`, генератор `res://tools/gen_hud.gd`)** — `CanvasLayer` (слой `10`) с прицелом-точкой, полоской/текстом здоровья, индикатором стойки и заглушкой боезапаса. Обновляется только по сигналам: `bind_player(player)` подписывает HUD на `HealthComponent.health_changed`/`died` и `StanceController.stance_changed`. Опроса в `_process` нет. При добавлении в сцену рядом с узлом `Player` HUD сам привязывается к нему (`_auto_bind_from_parent`).

## Данные оружия

- **`WeaponData` (`src/weapons/weapon_data.gd`)** — типизированный `Resource` с категориями и режимами огня, параметрами урона, боезапаса, обращения и необязательными ссылками на модели/звук. `cooldown()` переводит RPM в секунды; `damage_at(distance)` линейно интерполирует урон между `range_near` и `range_far`, ограничивая его на крайних дистанциях.
- **`src/weapons/data/*.tres`** — по одному временному профилю для `AR`, `SMG`, `LMG`, `DMR`, `SNIPER`, `SHOTGUN`, `PISTOL`, `LAUNCHER`; уникальные `id` имеют префикс `sample_`. Значения временные; на шаге 2.2 профили используются отдельным автоматом `Weapon`, без подключения к `Player`.

## Классы и проверка комплекта (шаг 3.1)

- [ClassData](src/classes/class_data.gd) — типизированный Resource: id, display_name, max_health, move_speed_mult, отдельные разрешённые категории основного/дополнительного оружия, gadget_slots и passive_perks. Пять собственных профилей [data/](src/classes/data/) описывают Assault, Medic, Support, Engineer и Recon; параметры и ограничения являются начальным балансом. Assault быстрее остальных; Support допускает LMG, Engineer — LAUNCHER, Recon — DMR/SNIPER, дополнительное оружие всех классов — PISTOL.
- [GadgetSlotData](src/classes/gadget_slot_data.gd) задаёт номер существующего слота Loadout и разрешённые EquipmentData.id. Каждый профиль описывает GADGET_1 и GADGET_2; данные включают подствольник, медицинское/ремонтное/противотанковое оборудование, снабжение, мины, засветку и маяк. Идентификаторы предметов и перков описывают роли; их механики в этом шаге не реализуются. Здоровье/скорость пока не применяются к игроку, инвентарь и сцены не изменены.
- [LoadoutValidator.validate](src/classes/loadout_validator.gd) — чистая статическая функция `(ClassData, Loadout) -> Array[String]`. Собирает ошибки категорий, недоступных слотов, запрещённых/пустых id и дубликатов гаджетов по id (включая разные ресурсы одного предмета). Порядок: primary, secondary, gadget_1, gadget_2; проверка не изменяет и не нормализует входные ресурсы. Каждый вызов возвращает отдельный массив. Отсутствующие аргументы возвращают ошибки без исключений.
- Сохранён контракт [Loadout](src/weapons/loadout.gd): null в любом слоте означает отсутствие предмета и разрешён. Отсутствующее разрешение слота или пустой allowed_ids запрещает непустой гаджет. Самостоятельный GRENADE_MELEE не относится к двум проверяемым слотам гаджетов. Валидатор не вызывает Input, симуляцию, урон или сетевые команды; проверка одинакова офлайн и в сети, а изменение игровой экипировки остаётся за существующей серверной логикой.
- [Тесты данных](tests/unit/test_class_data.gd) проверяют пять ресурсов, роли, уникальность/ссылки и все 80 сочетаний класс × категория × оружейный слот. [Тесты валидатора](tests/unit/test_loadout_validator.gd) проверяют полный/пустой комплект, null/неизвестные значения, отдельные разрешения слотов, разные виды дубликатов, накопление/порядок ошибок, независимость возвращаемых массивов и повторяемость без мутации исходных данных. Новых автолоадов, ассетов и представления нет.

## Базовый гаджет и размещаемый объект (шаг 3.2)

- [GadgetData](src/gadgets/gadget_data.gd) расширяет существующий EquipmentData, поэтому подходит двум слотам Loadout без смены их типов. Хранит max_charges, cooldown, reload_time и необязательную PackedScene размещаемого объекта. [base_gadget.tres](src/gadgets/data/base_gadget.tres) — нейтральный профиль: 2 заряда, кулдаун 0.5 с, перезарядка 1.5 с; это не конкретный предмет класса. Нефинитные/отрицательные длительности и отрицательная вместимость отклоняются при настройке.
- [GadgetContext](src/gadgets/gadget_context.gd) передаёт тик, source_id, родителя размещения и мировую позу из симуляции. Input и камера рендера не читаются. [Gadget](src/gadgets/gadget.gd) — Node без кадрового опроса: simulate(tick), use(ctx), can_use(), reload(tick). Сроки округляются вверх по ticks_per_second, минимум один тик даже при нулевой длительности. Повторные/старые тики не повторяют действия; один успешный use/reload на тик. can_use не меняет состояние, перед опросом вызывается simulate.
- Начальная setup выдаёт заряды только один раз. Успешное применение расходует один заряд и запускает кулдаун; исчерпанные заряды сами не восстанавливаются. Явная перезарядка блокирует применение, на сроке восстанавливает полный набор и не сокращает кулдаун. Пропуск тиков завершает её ровно один раз. Сигналы used, charges_changed, reload_started/reload_finished отделяют события от представления; запас/снабжение конкретных гаджетов не реализованы.
- [Deployable](src/gadgets/deployable.gd) — базовый Node3D для композиции размещаемых объектов. spawn(scene, ctx) создаёт только корень Deployable под живым Node3D в серверной ветке, устанавливает source_id/spawn_tick и мировую позу до входа в дерево. Неверная сцена/контекст не расходует заряд. despawn разрешён серверу и исполняется один раз. deployed/despawned и Gadget.deployable_created служат границей будущей репликации; RPC/сетевого спавнера пока нет, всё исполняется локально.
- [Game.is_server_or_offline](src/autoload/game.gd) проверяет фактический MultiplayerAPI (по умолчанию глобальный, компоненты передают API своей ветки), включая офлайн-сервер. Флаг запуска is_server не даёт клиентской ветке полномочий. Настройка, тики, применение, перезарядка, создание и удаление гаджетов не выполняются клиентом. Существующие компоненты не переведены на новый помощник.
- 23 теста в [test_gadget.gd](tests/unit/test_gadget.gd) и [test_deployable.gd](tests/unit/test_deployable.gd) проверяют заряды, точные сроки/округление, повторы/пропуски, события, независимость экземпляров, недопустимые данные, серверное размещение в повёрнутом/масштабированном родителе и запрет клиентских мутаций. Конкретные ящики/мины/маяки, игровые сцены, ввод и новый сетевой транспорт не добавлены.

## Аптечка и применение слотов (шаг 3.4a)

- [PlayerGadgets](src/player/player_gadgets.gd) создаётся PlayerEquipment один раз. Разрешения проверяет существующий LoadoutValidator; два слота используют Gadget, выбор Inventory и BTN_FIRE/BTN_RELOAD из PlayerInput. Удержание огня не повторяет деплой; смерть, нож, спринт и смена блокируют применение. Серверный MultiplayerAPI ветки проверяется до изменения состояния.
- [GroundDeployment](src/gadgets/ground_deployment.gd) использует кешированные запросы луча/объёма и [DeploymentConfig](src/gadgets/deployment_config.gd): земля, наклон, проход от игрока и свободный объём модели. Невалидное место не расходует заряд. Поза берётся из симуляции тела; камера рендера не читается. [medkit.tres](src/gadgets/data/medkit.tres) ссылается на собственную сцену, без цикла ресурсов.
- [MedicalBag](src/gadgets/medical_bag.gd) — композиция Deployable + [GadgetAura](src/gadgets/gadget_aura.gd) + [MedicalBagConfig](src/gadgets/medical_bag_config.gd). Area3D кеширует владельцев зон и число пересечений сигналами, удаление цели очищает кеш. В step(delta) нет поиска узлов, создания форм или массивов. Радиус проверяется по мировой позиции сущности; все живые получают 10 HP/с в сфере 4 м, без LOS. Раненые/мёртвые не восстанавливаются. Последний delta ограничен оставшимися 20 с, затем despawn.
- [medic_lab.tscn](src/gadgets/scenes/medic_lab.tscn) подставляет класс/профиль в экземпляр исходного полигона только в памяти. Примитивная сумка с белым крестом — собственный ассет. [medical_bag_acceptance.gd](tools/medical_bag_acceptance.gd) проверяет реальный ввод/деплой/лечение и сохраняет снимок Forward+. [GadgetBalanceReport](src/gadgets/gadget_balance_report.gd) добавляет значения ресурсов к воспроизводимому docs/BALANCE.md. Новых автолоадов и сетевого транспорта нет.

## Ящик снабжения и гранаты (шаг 3.4b)

- [AmmoCrate](src/gadgets/ammo_crate.gd) переиспользует Deployable/GadgetAura. [AmmoCrateConfig](src/gadgets/ammo_crate_config.gd) задаёт сферу 4 м, импульс раз в 1 с, 20% полного запаса каждого оружия (вниз до целого) и одну гранату. Вызывается существующий Weapon.add_reserve_ammo, магазины не меняются. Время между импульсами учитывается по delta, большой шаг объединяет пополнение; вместимость не превышается. Срок жизни и общий запас ящика не ограничены; снабжаются все живые Player в сфере без LOS, раненые исключены.
- GadgetContext/Deployable передают owner_id — идентификатор серверной сущности, назначаемый PlayerGadgets через get_instance_id; source_id сохраняет отдельный смысл источника урона. При деплое ящик просматривает группу только один раз и немедленно скрывает/отключает прежний ящик того же владельца под тем же родителем. Его step больше не снабжает до queue_free. Разные владельцы и миры независимы; автолоад/статический глобальный реестр не нужен.
- [GrenadeStockConfig](src/player/grenade_stock_config.gd) + [профиль](src/player/default_grenade_stock.tres): 3 гранаты при создании, максимум 3. PlayerProjectiles расходует одну только при успешном запуске существующего пула и публикует grenades_changed. Серверный add_grenades ограничивает вместимость, запрещён мёртвым/клиенту. [GrenadeStockView](src/ui/grenade_stock_view.gd) обновляется сигналами только у локального игрока без dedicated; прежний бесконечный учебный запас заменён конечным. Реанимация/респавн сами не пополняют запас, как и существующие патроны.
- [support_lab.tscn](src/gadgets/scenes/support_lab.tscn) выбирает Support/LMG/ящик только в памяти; [ammo_crate_acceptance.gd](tools/ammo_crate_acceptance.gd) проверяет деплой, реальную область, два оружия, гранаты и повторный деплой после перезарядки. Собственная примитивная модель/профили записаны в ASSETS.md и генерируемый баланс. Старая учебная AmmoBox полигона сохранена.

## Ремонтный инструмент (шаг 3.4c)

- [RepairToolData](src/gadgets/repair_tool_data.gd) расширяет GadgetData: дальность 4 м, 25 HP/с, нагрев 0.25/с, охлаждение 0.2/с, разблокировка при 0.35. [repair_tool.tres](src/gadgets/data/repair_tool.tres) разрешён существующим профилем Engineer. Непрерывный ремонт использует отдельный компонент [RepairTool](src/gadgets/repair_tool.gd), а не расход зарядов размещаемого Gadget; Inventory/PlayerInput/проверка класса общие.
- PlayerGadgets вызывает инструменты в монотонных тиках; актуальная поза головы берётся из симуляции. Кешированный луч world/vehicles/destructible с исключением владельца принимает только [RepairSurface](src/gadgets/repair_surface.gd), Area3D слоя vehicles с экспортируемой ссылкой на HealthComponent техники. Мир/дальность останавливают луч, полное/нулевое здоровье не чинится. Игрок/клиент не может подменить цель; прямой repair также проверяет сервер ветки.
- Один текущий тик восстанавливает HP и нагревает только за фактическое время до max_health/перегрева. На 100% ремонт блокируется до 35%; при удержании затем возобновляется. Отпускание, отсутствие цели, смена, спринт, нож и смерть прекращают ремонт, инструмент продолжает охлаждаться. Повторы/старые тики игнорируются; пропуски охлаждают, но не восстанавливают здоровье за прошлое.
- [RepairToolView](src/gadgets/repair_tool_view.gd) создаёт собственные примитивы инструмента/луча и шкалу один раз только локально без dedicated. Сигнал presentation_changed обновляет косметику; скрытие слота скрывает и CanvasLayer, новых узлов в кадре нет. Вертикальное направление луча получает безопасный up-вектор. Симуляция не зависит от представления.
- [engineer_lab.tscn](src/gadgets/scenes/engineer_lab.tscn) содержит [repair_fixture.tscn](src/gadgets/scenes/repair_fixture.tscn): примитивная приёмочная цель 300/500 HP с настоящими RepairSurface/HealthComponent. Это проверка компонента ремонта; управление/посадка/физика машины не реализуются. [repair_tool_acceptance.gd](tools/repair_tool_acceptance.gd) проверяет ввод слота, 325 HP за 1 с, 400 HP и перегрев за 4 с, охлаждение до 35% и постоянное число узлов, сохраняет два снимка Forward+. Новых автолоадов/RPC нет.

## Машина состояний оружия

- **`Weapon` (`src/weapons/weapon.gd`, `Node3D`)** — состояния `IDLE`, `FIRING`, `RELOADING`, `SWITCHING_IN`, `SWITCHING_OUT`, `BLOCKED`; явный вызов `simulate(inp: PlayerInput, blocked: bool)` раз в тик. Повторные и старые `inp.tick` игнорируются; пропущенные тики не воспроизводятся автоматически.
- Частота `ticks_per_second` берётся из `Engine.physics_ticks_per_second` и фиксируется на время симуляции. Интервалы из `WeaponData` округляются вверх до целого тика (минимум один): `next_fire_tick`, `reload_end_tick`, `switch_end_tick`. `Timer`, системное время и покадровые массивы не используются.
- `BTN_FIRE`/`BTN_RELOAD` читаются из `PlayerInput`; режимы `SEMI` и `BURST` требуют нового нажатия. Начатая очередь завершается после отпускания спуска. `cycle_fire_mode()` перебирает только разрешённые профилем режимы и отменяет остаток очереди, сохраняя задержку выстрела.
- `blocked` вычисляется вызывающей симуляцией движения (спринт/лестница/падение), запрещает начало стрельбы/перезарядки и отменяет очередь. Уже начатая перезарядка завершается по своему сроку; при сохраняющейся блокировке оружие затем переходит в `BLOCKED`.
- Боезапас: магазин `mag_size`, резерв `mag_size * reserve_mags`; перенос патронов только в конце `reload_time` либо `reload_empty_time`. `switch_out()` отменяет перезарядку без переноса патронов; после убирания оружие остаётся заблокированным до `switch_in()`. Обе смены используют имеющийся `draw_time`; команды отсчитываются от последнего обработанного тика и вызываются после него.
- Симуляция и команды разрешены только серверному `MultiplayerAPI` (включая офлайн-сервер); сетевой клиент не меняет состояние. Сигналы `fired(tick)`, `reload_started`, `reload_finished`, `ammo_changed(magazine, reserve)` отделены от представления. Лучи, урон, модели и интеграция с игроком на этом шаге не добавляются.

## Хитскан-стрельба и урон (шаг 2.3)

- **`WeaponHitscan` (`src/weapons/weapon_hitscan.gd`)** — компонент `Node3D`, связывающий сигнал `Weapon.fired(tick)` с существующим `HitscanQuery`. `setup()` кеширует оружие, идентификатор атакующего и RID тела/хитбоксов стрелка; повторная настройка заменяет подписку. `simulate(inp, aim, blocked)` передаёт ввод автомату оружия. Трассировка и применение урона разрешены только серверному `MultiplayerAPI`, включая офлайн-сервер.
- `Player.step_simulation()` передаёт оптическую позу камеры симуляции: `head.global_position`, `inp.yaw`, ограниченный `inp.pitch` и крен наклона. Поза не читает интерполированную камеру рендера и косметические `CameraEffects`. Оружие блокируется при спринте, в воздухе и после смерти. В сцену игрока и генератор добавлены `Weapon` с временным AR-профилем и `WeaponHitscan`.
- На один `fired` выполняется `WeaponData.pellets` лучей длиной `hitscan_range` (по умолчанию 1000 м). Конус задаёт максимальное отклонение от оптической оси, распределение равномерно по телесному углу. С шага 2.4 конус и направления вычисляет `WeaponHandling`, описанный ниже; каждый луч получает seed от атакующего, тика и номера дробины. Одинаковые ввод и мир дают одинаковые направления.
- **`DamageCalc.compute(weapon, distance, zone)` (`src/weapons/damage_calc.gd`)** — чистая функция: `weapon.damage_at(distance) × zone.damage_mult`, без изменения ресурсов, зоны или здоровья. Источник множителя — попавший `HitboxZone`; `WeaponData.headshot_mult`/`limb_mult` дополнительно не умножаются. Дистанция измеряется от начала луча до точки пересечения, геометрия мира останавливает луч.
- **`DamageEvent` (`src/weapons/damage_event.gd`)** — снимок одного попадания: `attacker` (идентификатор), `target` (сущность), `zone`, `damage`, `weapon` (id ресурса), `distance`, `point`. Положительный рассчитанный урон локально передаётся в `HealthComponent.apply_damage(damage, attacker, zone)`; затем испускается `damage_applied(event)`. `shot_traced` сообщает результат каждой дробины, включая промах и стену. Расход патрона остаётся ответственностью автомата `Weapon`: один патрон на все дробины выстрела.
- Внешние ассеты не добавлены. Необязательное пробитие поверхностей пропущено; параметр `penetration` пока не участвует в трассировке. Сетевой транспорт событий не добавлен.

## Отдача и динамический разброс (шаг 2.4)

- **`WeaponHandling` (`src/weapons/weapon_handling.gd`)** — чистое состояние `RefCounted`: накопленная отдача в градусах (`Vector2`: pitch вверх / yaw), добавочный разброс, индекс паттерна и последние принятые тик/выстрел. `advance(tick, ticks_per_second)` восстанавливает разброс со временем, отдачу — после `recoil_pause`; повторные/старые тики игнорируются. Пропущенные тики учитываются как прошедший интервал, без создания пропущенных выстрелов.
- На подтверждённый `Weapon.fired` после трассировки один раз вызывается `apply_shot()`: берётся следующий `recoil_pattern[i]`, после исчерпания — `recoil_fallback_deg` плюс ограниченный шум. Seed шума зависит от атакующего и тика с отдельным каналом; количество дробин не влияет на отдачу. Пауза сбрасывает индекс паттерна. `Weapon.configured` сбрасывает состояние при `setup()` оружия; повторная привязка хитскана заменяет подписки и сбрасывает обработку.
- `spread_degrees()` вычисляет `(base + bloom + speed * move_factor) * stance_mult` с ограничением `spread_max_deg`: `base` выбирается между `spread_hip_deg` и `spread_ads_deg`, в ADS добавка от стрельбы и движения умножается на `spread_ads_extra_mult`. Присяд и положение лёжа используют собственные множители. `bloom` растёт только после выстрела до `spread_max_bloom_deg`, затем линейно убывает. `spread_direction()` использует кешированный `RandomNumberGenerator`, seed от атакующего/тика/дробины и равномерный по телесному углу конус вокруг переданной оси.
- `Player` передаёт фактическую горизонтальную скорость и текущую стойку; ADS читается из уже существующего `PlayerInput.BTN_AIM`. `WeaponHitscan` применяет накопленную отдачу к позе симуляции до трассировки. Импульс текущего выстрела влияет на камеру и следующий выстрел. Камера использует ту же `aim_rotation()` с ограничением pitch ±89°, затем добавляет косметические `CameraEffects`; настройка косметики не отключает отдачу. `LocalInputReader` и `Head` сохраняют исходные углы: движение мыши компенсирует накопленное смещение.
- Все параметры находятся в `WeaponData` и восьми временных профилях `src/weapons/data/*.tres`. Новых узлов/автолоадов, сетевого транспорта и внешних ассетов нет. Клиентский `MultiplayerAPI` не выполняет авторитетную симуляцию, не трассирует лучи и не добавляет отдачу. Применяется существующая офлайн-серверная интеграция; визуальное оружие, анимация/FOV ADS сюда не входят.
- 19 тестов в `tests/unit/test_weapon_handling.gd` и `tests/unit/test_weapon_handling_integration.gd`: паттерн/шум и seed, независимость от RNG разброса, пауза/восстановление, пропуски/повторы тиков, рост/предел/затухание разброса, скорость/стойки/ADS, 8192 направления в повёрнутых конусах, компенсация, один импульс на дробовик, отсутствие импульсов при блокировке/перезарядке/на клиенте, сброс настройки и совпадение камеры с осью следующего выстрела на полигоне. Оценка ощущений остаётся обязательной ручной приёмкой.

## Боезапас и перезарядка (шаг 2.5)

- `Weapon.ammo_in_mag` — общее число доступных выстрелов, включая патронник. Начальное значение равно `mag_size`; тактическая перезарядка при ненулевом остатке достигает `mag_size + 1`, если `WeaponData.chamber_enabled`. Пустая перезарядка достигает только `mag_size`. У временного гранатомёта патронник отключён. Вместимость запаса — `mag_size * reserve_mags`.
- При старте запоминаются вместимость и срок: `reload_time` для тактической, `reload_empty_time` для пустой. Перенос из запаса происходит единожды на завершающем тике и ограничен недостающими патронами и остатком запаса. `reload_interrupt_on_sprint` отменяет перезарядку по фактическому `PlayerMotor.is_sprinting`, переданному через `WeaponHitscan`; блокировка воздухом сама по себе её не отменяет. `reload_interrupt_on_switch` разрешает отмену через существующий `switch_out()`, при отключении настройки смена отклоняется до завершения перезарядки. Отмена испускает `reload_cancelled`, обнуляет срок и сохраняет оба счётчика.
- Пустой спуск испускает `dry_fired(tick)` один раз на нажатие, без выстрела, лучей, отдачи и расхода запаса. `WeaponDryFire` — дочерний `AudioStreamPlayer` представления: один раз создаёт собственный короткий PCM-щелчок и проигрывает его по сигналу. Транспорт звука по сети не добавлен.
- `AmmoReceiver` — компонент игрока с экспортируемой ссылкой на `Weapon`. `add_ammo(fraction) -> int` добавляет долю полной вместимости запаса: `floor(capacity * clamp(fraction, 0, 1))`, ограничивает результат свободным местом и возвращает фактически добавленное количество. Нефинитные/неположительные значения игнорируются; магазин не меняется. `Weapon.add_reserve_ammo()` и сам интерфейс разрешены только серверному `MultiplayerAPI`, включая офлайн.
- `AmmoBox` — процедурный учебный ящик `Area3D` с маской слоя игроков. При `body_entered` вызывает интерфейс `AmmoReceiver`, сообщает `supplied(body, amount)` только при фактическом пополнении. Учебный источник не исчерпывается, повторный вход снова пополняет запас. На полигоне стоит в `(3, 0, 8)` рядом со спавном; генератор воспроизводит размещение. Гаджеты, инвентарь и новые команды ввода не добавлены.
- `HUD.bind_weapon()` подписывается на `ammo_changed`, сразу читает актуальные значения и отключает предыдущую подписку при перепривязке/выходе. На полигоне начальное показание — `30 / 150`; без оружия — `0 / 0`. Опроса в `_process` нет.
- 19 новых тестов: 2112 сочетаний магазина/запаса с патронником и без, длительности, отмена/повтор, опции смены/спринта, пустой спуск во всех режимах, дробное снабжение и границы, клиентский запрет, реальные физические входы в ящик, подписки HUD и передача фактического спринта в сцене игрока.

## Прицеливание и оптика (шаг 2.6)

- `WeaponAds` (`src/weapons/weapon_ads.gd`) — чистый компонент состояния. Симуляция принимает `PlayerInput.BTN_AIM`, `delta` и разрешение ADS; повторные/старые тики игнорируются. Линейная доля достигает 1 за `WeaponData.ads_time`, `smoothstep` сглаживает значения на концах. Отпускание/запрет разворачивает переход из текущей доли; нулевое время означает мгновенный переход.
- Отдельная `visual_fraction` движется покадрово к той же цели: тик не меняет FOV непосредственно. `FOV = lerp(base, base * ads_fov_mult, smoothstep(visual_fraction))`; `LocalInputReader` масштабирует исходную чувствительность отношением `tan(current_FOV / 2) / tan(base_FOV / 2)`, то есть обратным увеличением перспективной проекции. Изменение настройки базового FOV сохраняет текущую долю ADS.
- `Player` до перемещения передаёт `PlayerMotor` множитель `move_speed_mult * lerp(1, ads_move_speed_mult, smoothstep(fraction))`. Удержание разрешённого ADS запрещает спринт. `WeaponHitscan` получает долю из симуляции и смешивает hip/ADS-конусы, не читая камеру; трассировка, патроны и урон по-прежнему только на сервере. Локальный клиент может обновлять косметическое прицеливание. Смерть/имеющиеся состояния смены оружия запрещают ADS, `configured` сбрасывает переход.
- `WeaponAdsView` (`src/weapons/weapon_ads_view.gd`) под камерой локального игрока создаёт `WeaponData.viewmodel_scene` либо собственную временную сцену `temporary_viewmodel.tscn` один раз при настройке. Положение смешивается между ресурсными `viewmodel_hip_offset` и `viewmodel_ads_offset`. Ссылки на геометрию кешируются при создании; при включённой оптике прозрачность модели растёт вместе с ADS. Для удалённых игроков локальная модель не создаётся.
- `ScopeOverlay` (`src/ui/hud/scope_overlay.gd`) процедурно рисует круглую маску и сетку, прозрачность следует визуальной доле ADS. `CanvasLayer` 9 расположен под существующим HUD 10; `scope_overlay_enabled` управляет оптикой. Сетка перерисовывается при изменении размера, опроса узлов/создания объектов в кадровом обновлении нет. PIP/SubViewport, новые автолоады и сетевой транспорт не добавлены.
- 14 тестов покрывают длительности восьми профилей, формулу чувствительности и инверсию мыши, разворот/непрерывность FOV при 144 обновлениях, сброс/границы, замедление реального игрока, приоритет над спринтом, положение/затухание модели, оверлей, смену FOV, смерть, серверный разброс и запрет клиентских выстрелов. Сцена и генератор проходят полный check; снимки Forward+ просмотрены.

## Инвентарь и смена оружия (шаг 2.7)

- `Loadout` (`src/weapons/loadout.gd`) — ресурс пяти фиксированных слотов: основное, дополнительное, два гаджета, граната/нож. Первые два содержат `WeaponData`, остальные — `EquipmentData` (только идентификатор, имя и `draw_time`, без применения предметов). `null` обозначает пустой слот. Стандартный `data/default_loadout.tres` содержит AR и пистолет; слоты 3–5 пусты.
- `Inventory` (`src/weapons/inventory.gd`) создаёт экземпляры один раз при загрузке, использует имеющийся первичный `Weapon` сцены и хранит отдельные магазин, запас и режим каждого оружия. Серверная симуляция принимает команды `PlayerInput.weapon_slot`, `weapon_cycle`, `last_weapon`; повторные/старые тики игнорируются. Прямой слот имеет приоритет над колесом, колесо — над последним оружием; пустые слоты пропускаются, занятая смена не ставит новые команды в очередь. Смерть запрещает новые команды.
- Переход `READY → HOLSTERING → DRAWING → READY` использует существующие `Weapon.switch_out()`/`switch_in()`: убирание длится `draw_time` старого предмета, подъём — нового; округление вверх до тика, минимум один. Для оружия срок берётся из его `switch_end_tick`, для остальных предметов — из ресурса и частоты физики. Команда смены предшествует огню того же тика; отмена перезарядки учитывает существующую опцию. `advance_switch()` завершает срок до `switch_finished`, сохраняя возможность выстрела на завершающем тике. Смена не вызывает `Weapon.setup()` и не восстанавливает патроны.
- `active_slot_changed`, `switch_started`, `switch_finished` сообщают события вверх. Последний оружейный слот обновляется при фактическом убирании оружия; посещение гаджетов не стирает его. `LocalInputReader` буферизует события 1–5/колеса/T до следующего тика и затем очищает команды; автоповтор клавиш игнорируется. `switch_weapon_last` (T) добавлен в `InputMap`/`InputActions` (34 действия).
- `PlayerEquipment` (`src/player/player_equipment.gd`) однократно создаёт/настраивает хитскан-компоненты по экземплярам и прогревает модели `WeaponAdsView`. По событию меняются кешированные ссылки `Player.weapon`, `weapon_hitscan`, получателя снабжения и ADS; модели переключают видимость без инстанцирования при смене. Для неоружейного слота оружие/ADS отключены. `HUD` перепривязывает `ammo_changed` по событию инвентаря, отключая прежнюю подписку. Новых автолоадов, ассетов и сетевого транспорта нет.
- Сцена игрока и генератор включают `Inventory`/`PlayerEquipment`. В генераторе компонент с зависимостями от `Player` загружается динамически в `_initialize()`, после регистрации автолоадов, чтобы запуск `SceneTree`-скрипта не компилировал `Events`/`Settings` раньше времени.

## Viewmodel и процедурная анимация (шаг 2.8)

- `WeaponAdsView` сохраняет ADS-смещение, оптику и кеш комплекта; модели находятся в отдельном `ViewmodelRig` под камерой. Rig создаётся при прогреве только для локального игрока. Смена выбирает кешированную модель, перепривязывает сигналы и сбрасывает косметическое состояние без создания объектов в кадровом/физическом обновлении.
- В Godot `4.7.2` наличие `BaseMaterial3D.use_fov_override`/`fov_override` проверено через ClassDB, семантика — по документации latest. Материалы моделей используют независимый вертикальный FOV (по умолчанию 75°), `no_depth_test`, прозрачный проход и приоритет 127; тени отключены, occlusion culling игнорируется. Модель остаётся перед стеной; геометрия мира и серверные лучи не меняются. SubViewport не нужен.
- При прогреве каждый меш и его материалы копируются. Исходная процедурная сцена и другие экземпляры не изменяются. Использование индивидуальных материалов в копии меша устраняет обнаруженную ошибку dummy-renderer при повторном немедленном освобождении сцен с surface override; этот жизненный цикл покрыт тестом.
- `ViewmodelConfig` (`src/weapons/viewmodel_config.gd`, `data/default_viewmodel.tres`) содержит FOV, частоту пружин, параметры sway/bob/kick/спринта, позу и кривую перезарядки. `WeaponData.viewmodel_config` позволяет заменить профиль; при отсутствии используется общий ресурс.
- `ViewmodelSpring` — аналитическое решение критически затухающей пружины Vector3. `ViewmodelMotion` принимает суммарное изменение углов мыши и состояние движения, считает ограниченный sway по угловой скорости, bob по пройденному расстоянию на земле, позу спринта и перезарядку по кривой. Две пружины сглаживают смещение и поворот по render-delta; глобальный Input не читается. Нулевой/отрицательный/нефинитный delta игнорируется.
- `Weapon.fired` даёт один косметический импульс, `reload_started` выбирает тактическую/пустую длительность, `reload_finished`/`reload_cancelled` возвращают модель. Представление не изменяет патроны, отдачу камеры, хитскан или урон. `Player` передаёт изменение углов после существующего ввода и фактические скорость/землю/спринт в покадровое обновление.
- Проверки покрывают математику при 5–360 FPS, большой delta, затухание, sway/bob/спринт/кривую и сброс, материалы/FOV, сигналы, перепривязку, реальные ввод и стрельбу, отсутствие rig у удалённого игрока. Forward+ снимки проверяют стену с контрольным depth-test, FOV 60/90/120, позы и ADS. 2026-10-27 пользователь подтвердил выполнение обязательной человеческой приёмки, шаг 2.8 принят (`DONE`). Новых автолоадов и внешних ассетов нет.

## Косметические эффекты стрельбы (шаг 2.9)

- `ShotEffects` создаётся `PlayerEquipment` при загрузке игрока и подписывается на `WeaponHitscan.shot_traced` / `damage_applied` всех заранее подготовленных оружейных слотов. При смене оружия сохраняются те же пулы. Повторная привязка источника не дублирует подписки. `WeaponHitscan.shot_origin` — свойство только для чтения позы симуляции; эффекты не читают ввод и не вызывают симуляцию, расход патронов или урон. Отдельный `present_trace()` позволяет проверить косметику независимо от игровой логики; сетевой транспорт в этот шаг не входит.
- `ObjectPool` — фиксированное кольцо узлов, прогретое фабрикой. При исчерпании новый эффект вытесняет самый старый; расширения, удаления или инстанцирования в обработчиках выстрела и кадра нет. Каждый компонент стрелка имеет пулы вспышек/трассеров/гильз/импактов из `ShotFxConfig`, кольцо **256 `Decal`** и пул **32 `AudioStreamPlayer3D`**. Это локальные компоненты сцены, новых автолоадов нет; у выделенного сервера `ShotEffects` не создаётся.
- `MuzzleFlash` содержит прогретые `GPUParticles3D` и `OmniLight3D`: частицы перезапускаются, свет выключается на следующем render-кадре. При большом delta корень вспышки сохраняется минимум до этого кадра. Локальная вспышка использует FOV материала viewmodel и её позу; мир и серверные лучи не меняются. `ShotVisual` обновляет тонкий летящий меш трассера, аналитическую баллистику/вращение гильзы и расширение/затухание импакта без физических тел. Трассер обрезается фактической точкой попадания и показывается для каждого N-го выстрела; дробины разделяют одну вспышку, гильзу и звук выстрела.
- `ShotSurface` читает `surface_type` фактического коллайдера: `concrete`, `earth` (`dirt`/`ground`), `metal`, `wood`, `flesh`, `water`. Отсутствующее/неизвестное значение означает бетон; хитбокс или компонент здоровья имеет приоритет плоти. Шесть заранее созданных мешей/материалов различают пыль, землю, искру, щепку, кровь и водяное кольцо. Декали ориентируются по нормали, на плоти и воде отверстия не создаются.
- `ShotFxAssets` синтезирует меши, текстуру отверстия и четыре PCM-потока только при прогреве; `WeaponData.fire_sound` имеет приоритет над процедурным выстрелом. Пул голосов используется также для обычного/головного попадания и whiz. Последний разрешён только чужому выстрелу, если ближайшая внутренняя точка фактического отрезка луча проходит в заданном радиусе слушателя: стена перед ним, концы отрезка и прямое попадание не дают ложный пролёт.
- `HitMarker` — один заранее созданный `Control` на локальном слое 11, с четырьмя штрихами и ограниченным временем видимости. Подтверждается только положительным `damage_applied`; трасса или попадание в геометрию сами по себе маркер не показывают. `ShotFxConfig` + `src/fx/default_shot_fx.tres` хранят параметры представления; исходные оружейные ресурсы и геометрия полигона не изменялись.
- Юнит-тесты проверяют кольца, поверхности/базисы, отрезок whiz, время света/эффектов, звук/маркер, повторную привязку, смену оружия, выделенный сервер, сохранение урона/боезапаса/отдачи и число узлов за 1800 тиков. `tools/shot_fx_soak.gd` выполняет не менее 30 реальных секунд автоматического огня при 900 RPM по шести поверхностям, проверяет счётчик узлов на каждом тике и сохраняет снимки при Forward+. Увеличенный магазин и нулевые разброс/отдача используются только в проверочном скрипте.

## Гранаты и снаряды (шаг 2.10)

- `ProjectileData` (`src/weapons/projectiles/`) — ресурсы `frag.tres`, `smoke.tres`, `flash.tres`, `rocket.tres`: гравитация, линейное сопротивление, скорость, запал, отскок/трение, радиус, урон, маски и длительности эффектов. Осколочная граната взрывается через 3 с; ракета — при контакте либо по предельному запалу. Профили временные.
- `ProjectileBallistics` аналитически решает `dv/dt = gravity - drag * velocity`; при нулевом сопротивлении получается парабола. Совпадение при разбиении времени проверяется с допуском для 32-битных компонентов `Vector3`. `Projectile.simulate(delta)` проверяет сегмент каждого тика кешированным `PhysicsRayQueryParameters3D`, отражает нормальную скорость и гасит касательную. Остаток времени проходит после отскока; ограничение числа контактов оставляет снаряд у последней поверхности. Покой не останавливает запал, большой delta ограничен моментом взрыва.
- `ProjectileSystem` — локальный компонент сцены с заранее созданными 16 `Projectile`, без `RigidBody3D` и новых автолоадов. Активные игровые снаряды не вытесняются: заполненный пул отклоняет бросок/блокирует выстрел гранатомёта. После взрыва переиспользуется тот же объект. Система и эффекты закреплены в мировых координатах. На сервере/офлайн работают запуск, баллистика и `Explosion.apply`; клиентский `MultiplayerAPI` их не исполняет.
- `Explosion` использует прогретый сферический запрос по слою хитбоксов (до 4096 результатов), собирает уникальные `HealthComponent`, предпочитает центр торса и проверяет линию видимости через `world | vehicles | destructible`. Формула: `max_damage * clamp(1 - distance / radius, 0, 1)`, за стеной — 0. Множители головы не применяются; самоповреждение разрешено. Маска окклюзии отделена от маски движения, хитбоксы не закрывают взрыв друг от друга. Сигнал `damage_applied` передаёт фактический положительный расчёт, источник и здоровье.
- `PlayerInput.throw_grenade` — однократная команда, буферизуемая `LocalInputReader` по существующему G; автоповтор клавиши игнорируется. `PlayerProjectiles` получает её от `Player.step_simulation`, проверяет смерть, монотонный тик и ресурсный интервал. Поза броска берётся из головы симуляции и углов ввода; RID стрелка исключены только из движения, не из взрыва. На учебном полигоне G бросает неограниченный запас осколочных гранат с интервалом 0.8 с; профиль компонента можно заменить на дым/светошумовую. Учёт носимого запаса гранат в шаг не входит.
- `WeaponData.projectile_data` переводит выстрел существующего `WeaponHitscan` в `ProjectileSystem.launch` с теми же позой, серверным разбросом, отдачей и расходом одного патрона. `launcher.tres` использует `rocket.tres`: мгновенного hitscan-урона/`shot_traced` нет, урон наносится взрывом при столкновении. `PlayerEquipment` связывает все оружейные слоты с общим пулом игрока. Стандартный комплект AR + пистолет не меняется.
- `ProjectileEffects` слушает `ProjectileSystem.exploded`, обновляет заранее созданные модели снарядов и кольцо из 16 `ProjectileVisual`. Собственные сферические примитивы расширяются/затухают; дым закрывает изображение 12 с, без игровой коллизии. Локальные ослепление/оглушение и процедурный PCM-звон зависят от дистанции/стены; светошумовая учитывает направление камеры. Более слабое оглушение не отменяет сильную вспышку. Представление не применяет урон и не меняет ввод/движение; выделенный сервер не создаёт его. `present()` — вход косметического события, сетевой транспорт пока отсутствует.
- Тесты проверяют формулу и настоящую стену, дедупликацию, точный запал/покой, сопротивление, отскок и остаток тика, тонкие стены/высокую скорость, лимит контактов, исключение тела, ракету по хитбоксу, 300 повторных запусков без роста узлов, клиентский запрет, ввод/смерть, дым/сенсорные эффекты, мировые координаты и выстрел гранатомёта. `tools/projectile_acceptance.gd` использует исходный полигон без изменения сцены, проверяет 180 тиков и сохраняет пять снимков Forward+ в `.godot/`; зелёные метки траектории существуют только в проверочном скрипте.

## Ближний бой (шаг 2.11)

- `MeleeData` (`src/weapons/melee_data.gd`, `data/knife.tres`) хранит дальность 1.5 м, обычный урон 50, задержку контакта 0.2 с, длительность 0.7 с, интервал 0.8 с и параметры процедурного представления. Задний конус задаётся `rear_dot = 0.5`: горизонтальная ось цели и направление от неё к атакующему дают dot ≤ −0.5 (±60° от спины); высота/положение камеры не определяют спину.
- `MeleeAttack` — отдельный серверный компонент с монотонными тиками и сроками, округлёнными вверх по частоте физики. `PlayerInput.melee` — однократная команда V из `LocalInputReader`, автоповтор игнорируется. Один кешированный луч выполняется только на сроке контакта по текущей позе головы симуляции; кеш RID исключает тело и хитбоксы атакующего. Мир/техника/разрушаемая геометрия останавливают луч; ближайший хитбокс получает один урон без множителей головы/конечностей. Со спины снимается всё текущее здоровье, источник передаётся в `HealthComponent`.
- `PlayerEquipment` создаёт нож при загрузке, `Player` вызывает его после перемещения/обновления головы. Во время удара блокируются выстрел, бросок, ADS и новые команды смены; уже начатые смена/перезарядка запрещают новый удар, команда смены того же тика имеет приоритет. Смерть отменяет ожидающий контакт. Пропуск тиков разрешает контакт один раз, повторные/старые тики не создают событий; отклонённые команды не ставятся в очередь. На клиентском `MultiplayerAPI` урон и сроки не исполняются.
- `MeleeView` — отдельное представление под камерой локального игрока: две собственные прогретые геометрии с независимым FOV, без теста глубины/теней; сигналы `attack_started` / `attack_finished` запускают и останавливают процедурный замах → контакт → возврат. На время удара скрываются оружие/оптика, затем возвращаются. Косметика не применяет урон, не создаётся удалённому игроку/выделенному серверу и не создаёт узлов в кадре. Новых автолоадов, внешних ассетов и сетевого транспорта нет.
- 21 тест проверяет лицо/спину при 500 HP, геометрию заднего конуса при четырёх поворотах, зоны, 1.5 м/стену, актуальную позу на контакте, сроки/повторы/пропуски, смерть, клиентский запрет, ввод V и взаимодействие с оружием/инвентарём. 100 повторных анимаций сохраняют число узлов. `tools/melee_acceptance.gd` запускает настоящий полигон и сохраняет шесть снимков в `.godot/`; headless/Forward+ подтверждают лицо 100→50, спину 500→0, 827 узлов и неизменный боезапас.

## Жизненный цикл хитбоксов

- `PlayerHitboxes` однократно находит или создаёт зоны и кеширует ссылки на зоны и формы. Формы из сцены дублируются только при первой инициализации, чтобы каждый экземпляр владел своим ресурсом; для новых зон формы создаются сразу без лишнего дублирования. Повторные `setup()`, `_ready()` и обновления стойки используют те же формы и RID. Обновление геометрии не выполняет поиск узлов и не создаёт формы или массив зон заново.

## Тренировочные мишени

- **`TargetDummy` (`res://src/maps/testbed/target_dummy.tscn`, `res://src/maps/testbed/target_dummy.gd`, генератор `res://tools/gen_target_dummy.gd`)** — `Node3D` без физического тела: `HealthComponent` + `PlayerHitboxes` (стойка `STAND`, слой `hitboxes`) + узел `Visuals`. Режимы: стоячий или патруль по `waypoints` со скоростью `move_speed` (`set_patrol_path`). При `died` хитбоксы отключаются, визуал скрывается, через `respawn_delay` (3 с) вызывается `HealthComponent.reset()`. Логика шага вынесена в `step(delta)` и вызывается из `_physics_process`, поэтому тестируется детерминированно.

## Генерация сцен и полигон (`Testbed`)

- **Генераторы сцен (`tools/gen_*.gd`)** — сцены создаются воспроизводимыми headless-скриптами (`PackedScene.pack()` + `ResourceSaver.save()`).
- **Тестовый полигон (`res://src/maps/testbed/testbed.tscn`, генератор `res://tools/gen_testbed.gd`)** — уровень 200×200 м с процедурным шейдером метровой сетки (`res://src/maps/testbed/grid_1m.gdshader`), окружением `WorldEnvironment`, солнцем `DirectionalLight3D`, точкой спавна `PlayerSpawn`, препятствиями для тестирования передвижения (стены 1.0–3.0 м, рампы 15°/30°/45°, лестница 0.2 м, коридор 0.8 м, туннель 1.0 м) и стрельбищем (`ShootingRange`, мишени на 10/25/50/100/200 м), узлом `Targets` с 5 экземплярами `TargetDummy` (3 стоячие, 2 патрульные), а также `HUD` и `DebugOverlay`. Все коллайдеры находятся на физическом слое `world` (`1`).

## Поток данных: ввод → симуляция → представление

1. **Ввод (`PlayerInput`, `LocalInputReader`)** — структура ввода за один физический тик (`res://src/player/player_input.gd`: направления `move`, углы взгляда `yaw`/`pitch`, битовая маска кнопок `buttons`, номер тика `tick`). На клиенте-владельце `LocalInputReader` (`res://src/player/local_input_reader.gd`) собирает `PlayerInput` из глобального `Input` исключительно через `StringName`-константы `InputActions` (`res://src/core/input_actions.gd`), накапливает `yaw` и ограничивает `pitch` диапазоном `±89°` с учётом `sensitivity` и `invert_y` из `Settings`.
2. **Симуляция (`PlayerStance`, `StanceController`, `PlayerMotor`, `MovementConfig`, `HealthComponent`, `HitboxConfig`, `HitboxZone`, `PlayerHitboxes`, `HitscanQuery`, `Player`)** — детерминированный расчёт стоек, наклонов, бега, прыжка, подъёма на ступени, приземления, здоровья и хитбоксов по `PlayerInput`, ресурсу параметров `MovementConfig` (`res://src/player/movement_config.gd`, `res://src/player/default_movement.tres`) и `delta` (60 Гц) без прямых обращений к `Input.*`. Компонент `StanceController` (`res://src/player/stance_controller.gd`, перечисление `PlayerStance` в `res://src/player/player_stance.gd`) управляет стойками `STAND` / `CROUCH` / `PRONE` (высота капсулы `1.8` / `1.2` / `0.5` м, высота камеры `1.65` / `1.05` / `0.35` м, фиксация ступней через `CollisionShape3D.position.y = height * 0.5`), проверяет препятствия над головой через `CharacterBody3D.test_move(...)`, выполняет подъём `PRONE -> CROUCH -> STAND` за `0.6` с и рассчитывает наклоны (`BTN_LEAN_L`/`BTN_LEAN_R`, `±15°` и смещение головы `±0.4` м) с проверкой стены через переиспользуемый `PhysicsRayQueryParameters3D`. `PlayerMotor.simulate(body, inp, cfg, stance, delta)` (`res://src/player/player_motor.gd`) разрешает спринт только вперёд (`sprint_min_forward_dot = 0.5`) в стойке `STAND`, управляет опциональной выносливостью (`stamina_enabled = false` по умолчанию), поддерживает `coyote_time = 0.1` с, выполняет автоподъём на ступени до `0.35` м (`test_move` вверх → вперёд → вниз с переиспользуемым `KinematicCollision3D` без вертикального подпрыгивания) и при приземлении вычисляет урон от падения при вертикальной скорости ниже `−12` м/с (`MovementConfig.calculate_fall_damage`). Универсальный узел `HealthComponent` (`res://src/core/health_component.gd`) хранит `max_health`, `current`, `is_dead`, обрабатывает `apply_damage(amount, source_id, zone)`, `heal(amount)`, `reset()` и опциональную регенерацию (`regen_delay`, `regen_rate`, отключена по умолчанию), испуская сигналы `health_changed`, `damaged`, `died`. Зона попадания `HitboxZone` (`res://src/player/hitbox_zone.gd`, `Area3D` на физическом слое `hitboxes` = `4`, `collision_mask = 0`, `monitoring = false`) хранит `zone` (`HEAD`, `TORSO`, `ARMS`, `LEGS`), множитель урона `damage_mult` из ресурса `HitboxConfig` (`res://src/player/hitbox_config.gd`, `res://src/player/default_hitboxes.tres`) и ссылку на `HealthComponent` владельца. Узел `PlayerHitboxes` (`res://src/player/player_hitboxes.gd`) создаёт набор зон по размеру капсулы (`HeadZone` — `SphereShape3D`, `TorsoZone`/`LeftArmZone`/`RightArmZone`/`LegsZone` — `BoxShape3D`) и динамически подстраивает их под высоту капсулы, высоту головы и смещение наклона `lean_offset` в текущей стойке. Метод `HitscanQuery.cast(from, to, exclude)` (`res://src/weapons/hitscan_query.gd`) трассирует луч с `collide_with_areas = true`, `collide_with_bodies = true` и маской `world + hitboxes` (`5`) через переиспользуемый `PhysicsRayQueryParameters3D`, возвращая `HitResult` (`res://src/weapons/hit_result.gd`: `hit`, `position`/`point`, `normal`, `zone`, `damage_mult`, `target`, `health_component`, `hitbox`, `entity`, `collider`, `rid`). Сцена игрока `res://src/player/player.tscn` (`Player`, генератор `res://tools/gen_player.gd`) представляет `CharacterBody3D` на слое `players` (`2`) с маской `world` (`1`), капсулой `1.8 × 0.35` м и узлами `Head`/`Camera3D`/`CameraEffects`, `StanceController`, `HealthComponent` и `Hitboxes`. Игровая логика (урон, смерть, захват, боезапас) авторитетна на сервере.
3. **Представление (`Camera3D`, `CameraEffects`)** — глобальная физическая интерполяция (`physics/common/physics_interpolation=true`) сглаживает перемещение `Player` и `Head` между тиками 60 Гц, тогда как `Camera3D` (`physics_interpolation_mode = OFF`) каждый кадр рендера (`_process`) берёт интерполированную мировую позицию головы `get_global_transform_interpolated() * head.position`, актуальные углы `yaw`/`pitch`, угол крена наклона `head.rotation.z` и чисто визуальное смещение/покачивание из узла `CameraEffects` (`res://src/player/camera_effects.gd`, отключается настройкой `camera_effects` в `Settings`). Захват курсора (`MOUSE_MODE_CAPTURED`) выполняется при старте локального игрока и освобождается по `InputActions.PAUSE_MENU` (`Esc`).

## Сетевая модель

- Выделенный headless-сервер (`ENetMultiplayerPeer`) + клиенты.
- Клиент предсказывает собственное перемещение и выполняет сверку (reconciliation) с серверными снапшотами.
- Удалённые сущности отображаются через буфер интерполяции.

## Соглашения по именованию

- Файлы и каталоги: `snake_case`
- Классы (`class_name`): `PascalCase`
- Константы и элементы `enum`: `UPPER_SNAKE`
- Сигналы: глаголы в прошедшем времени (`health_changed`, `player_died`)
- Приватные поля и методы: префикс `_` (`_velocity`, `_apply_recoil()`)
- Отступы: табы (`\t`), переводы строк `LF`
